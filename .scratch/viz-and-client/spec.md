# Spec：可视化与客户端 · 信任纵切 MVP（M0–M2）

Status: ready-for-agent

**依据文档：** 需求 `docs/design/2026-10-13-viz-and-client-spec.md`（v1.3）· 决策 `docs/design/2026-10-13-trust-first-family-archive.md` · `ADR-0005`（核对落库数据模型）· `ADR-0006`（局域网无鉴权）· 统一语言 `CONTEXT.md`（检查单 / 图像 / OCR 结果 / 报告 / 报告类别 / 指标项 / 成员 / 家长 / 核对 / 修正对——本 spec 沿用该词汇）。

## Problem Statement

家长（不懂检验医学的普通人）把医院检查单拍照归档时，面对三个现实：纸质单据可信但会丢、拍完就散落在相册里；现有的识别工具是只有开发者能用的命令行；OCR 识别不完美，屏幕上的数字不敢直接信。家长需要的是：在 30 秒内把一张检查单变成**可信、可比、长期不丢**的家庭健康档案——屏幕上的每个数要么来自高置信识别、要么经家长亲手确信。

## Solution

一个面向家庭成员标签的健康档案 App（React + Expo，TypeScript，单工程）：家长为家庭各成员（孩子为重点，成员 = 显示名 + 是否孩子两档信息）拍照上传检查单，家庭局域网内的后端在数秒内同步识别为结构化报告；识别干净的报告免核对直落成员档案，需要核对的报告（部分产出/失败/低置信项）在纸还在手边时当场逐项确认或修正——图像对应区域 ↔ 原始 OCR 行文 ↔ 解析值三方对照；档案（报告时间线、详情）只呈现核对过的可信数字。弱网拍照进本地离线队列，回家自动补传；扫码一次完成后端配对。全程家庭内网、不做鉴权。

## User Stories

1. 作为家长，我想在 App 里拍一张检查单并在几秒内看到结构化报告，以便纸还在手边时就能开始核对。
2. 作为家长，我想在上传前选择或确认报告归属的成员，以便家庭档案按人组织、互不混淆。
3. 作为家长，我想只用名字 + 是否孩子两档信息创建成员，以便几十秒内配好全家档案。
4. 作为家长，我想让成员列表里孩子永远排在前面，以便重点成员触手可及。
5. 作为家长，我想给成员改名，以便手滑打错时不必删除重建。
6. 作为家长，我想在医院弱网下拍照时照片仍进入本地队列，以便后端不可达不阻塞我拍照归档这件事本身。
7. 作为家长，我想回家连上局域网后队列自动重试上传，以便拍完不用惦记着手动补传。
8. 作为家长，我想同一张照片重复上传只归档一份，以便重试和误操作不污染档案。
9. 作为家长，我想从队列里删除误拍的照片，以便队列干净，且删除不影响已归档的报告。
10. 作为家长，我想对识别干净的成功报告免核对、轻提示后直接归档，以便日常归档零摩擦。
11. 作为家长，我想只有部分产出/失败/含低置信项的报告才进入核对流程，以便核对是例外而非常态负担。
12. 作为家长，我想当场核对时在图像对应区域、原始 OCR 行文与解析值之间逐项对照，以便我确信的每个数都亲眼看过。
13. 作为家长，我想低置信项在详情页保持高亮并可在阅读时顺手核对，以便当场来不及的回家补上。
14. 作为家长，我想核对界面是逐项列表加确认/修正按钮，以便快速扫过且误确认难以发生。
15. 作为家长，我想修正数值、单位、名称、参考范围四个纸面事实，以便识别错什么我就能改什么。
16. 作为家长，我想异常标记由后端按修正后的值 × 参考范围自动重算，以便我既不必也无从造出颜色与数值矛盾的档案。
17. 作为家长，我想对任意指标项发起修正（即使它是高置信项），以便发现明显错值时永远有出口。
18. 作为家长，我想改完之后还能再改，以便没有任何"定局"把我锁死。
19. 作为家长，我想报告的"剩余 N 项未核对"由后端自动派生，以便没有作业可提交、也就没有作业被放弃。
20. 作为家长，我想报告时间线按成员过滤并显示状态与按标记聚合计数的徽标，以便一眼知道谁有什么值得留意。
21. 作为家长，我想详情页把当前值画在参考范围条带上的位置，以便不懂检验医学也能看懂正常与否。
22. 作为家长，我想失败的报告展示图像与失败原因，以便判断要不要重拍（且它不计入待核对数）。
23. 作为家长，我想在失败报告旁重新拍照生成新报告，以便有出口且原报告留痕。
24. 作为家长，我想把归属传错的报告改派给正确的成员，以便传错不必删档重传。
25. 作为家长，我想删除误传或拍糊的报告，以便档案干净（原始图像与识别历史留痕保留）。
26. 作为家长，我想扫一枚配对二维码就配好后端地址，以便不懂网络也能一次配好。
27. 作为家长，我想手输地址兜底，以便扫码失败也不至于卡住。
28. 作为家长，我想一张什么都没拍到的照片被记为失败留痕而不是"空报告归档"，以便不会出现"以为归档了其实什么都没有"。
29. 作为家长，我想离线补传完成时被提醒"N 项待核对"并直达核对，以便纸已不在手边的报告不被遗忘。
30. 作为开发者家长，我想后端只是既有二进制新增的一个 serve 子命令，以便家庭常驻部署就是跑一条命令加原 compose 栈。
31. 作为开发者家长，我想 Mac（arm64）与 NAS（amd64）两处用同一份 compose（镜像双架构），以便开发验证环境与家庭常驻环境同构。
32. 作为开发者家长，我想每次改动先过 Expo 验证环境门禁再上真机，以便迭代准确、App 门禁不虚报完成。
33. 作为开发者家长，我想识别端契约与存量 golden 本期完全不动，以便识别回归不需要背客户端特性这口锅。
34. 作为家长，我想一切数据只在家中局域网流转，以便健康数据隐私默认安全。
35. 作为家长，我想界面和文案停在中性事实侧、绝不出现诊断/处方/解读，以便这个工具不会越界成为"医疗建议机"。

## Implementation Decisions

**服务形态与部署（ADR-0006）**
- 后端 HTTP 服务是既有 CLI 二进制的 `serve` 子命令，复用既有的编排依赖层（存储 / 识别器 / 对象存储三个接口），不建第二个二进制。
- 部署沿用既有 compose 栈（Postgres / 对象存储 / 识别服务已在），仅新增数据服务一个容器；家庭常驻实例 = NAS（amd64）、开发验证实例 = Mac（arm64），同一份 compose 两处复用、镜像双架构构建。
- 局域网先行、不做鉴权；配对二维码内容为纯 URL 常量（路由器 DHCP 保留 IP），手输兜底同串。

**契约与 API 面（M0 冻结）**
- HTTP 契约唯一源 = OpenAPI 3.1 单文件，识别端既有 JSON Schema 通过引用复用；识别端契约（JSON Schema + pydantic + Go 三方互证）与存量识别 golden **完全不动**，本期 golden 仅新增 HTTP fixtures。
- API 前缀 `/api/v1`。12 个端点定稿：

| 方法与路径 | 用途 | 关键约定 |
| --- | --- | --- |
| GET health | 配对后连通性校验 | 返回 ok 与版本 |
| GET members | 成员列表 | 返回是否孩子与创建时间；排序客户端做 |
| POST members | 建成员 | `name` + `is_child` |
| PATCH member | 改名/改是否孩子 | 不提供成员删除 |
| POST reports | 上传（multipart：图像 + 成员） | 同步返回完整报告（NF-04 <3s）；图像内容哈希命中已有 → 200 + duplicate 标记 + 已有报告（幂等） |
| GET reports | 时间线 | 按成员过滤；含状态、未核对低置信计数、按 flag 异常计数 |
| GET report | 详情 | 指标项含稳定外部 id、核对状态、OCR 行链接（行号 + 框坐标）、B2-lite 上一值 |
| GET image | 图像 | 后端代理对象存储，局域网直出 |
| PATCH report item | 核对（确认/修正） | 修正只收 value/unit/name/ref_range；flag 服务端重算；响应含报告级状态（单响应刷新整屏） |
| PATCH report | 改归属 | 换成员归属 |
| DELETE report | 删除 | 硬删报告与指标项与修正对；图像与 OCR 历史留痕 |
| GET trend | B2 趋势时序 | 单位门控参数；M4 消费、M0 冻结 |

- 数据库新增迁移：成员表；报告表加成员归属（可空，存量 CLI 时代报告无主）与 `fail_reason`（识别失败原因，由流水线产出）；指标项表加核对状态；新增 append-only 修正对表。
- 指标项以内部自增 id 的不透明句柄暴露；对已含核对决策的报告重跑识别 → 409 拒绝（显式覆盖才放行）；未核对报告重跑会换 id，客户端刷新详情即取到新 id。

**成员域**
- 成员最小模型 = 显示名 + 是否孩子（孩子/成人两档），仅此二字段；无生日、头像，不支持删除（可改名）。
- 一份报告恰好归属一个成员（schema 在报告表挂成员，不在指标项挂）；多成员混单（家庭套餐）是已知限制，P2+ 再议。

**核对域（ADR-0005）**
- 家长可修正的纸面事实 = value / unit / name / ref_range 四项；`flag` 一律服务端按修正后的 value × ref_range 重算，不接受手改。
- 落库真源：指标项永远装最终生效值，下游（时间线/详情/趋势/聚合）无脑读它；修正历史进 append-only 修正对表（before→after 全集 + 原始行文 + OCR 行号 + 时间），本期只存不回流，形状按可回流设计供未来喂评价工具。
- 核对状态机（拷问会定稿）：

```text
指标项核对状态：未核对 --确认|修正--> 已确认|已修正
  · 任何状态可再次确认或修正；每次修正 append 一条修正对（before = 上次生效值）
  · 最终状态 = 最后一次动作；确认不产生修正对记录
  · 无「撤销回未核对」——误确认的出口是修正
报告状态派生：failed / success 恒定
  · partial → success 当且仅当「未核对低置信项计数」= 0；单向，永不回退
```

- `unreviewed_low_confidence_count` 为响应派生字段（不落列），只统计 `partial` 报告中未处理的低置信指标项；`failed` 不计入。
- 核对 UI 以**逐项列表 + 确认/修正按钮**为 POC 基线（横滑仅作对照，M1 前 POC 定稿）。

**上传与离线**
- 上传为 multipart 原子接收（无分片断点续传），同步等待识别结果；客户端离线队列在回到局域网（App 前台）时自动重试，SHA256 幂等保证重试安全；队列项删除不碰已归档报告。
- M1 语义 = 「前台自动重试」（Expo Go 可验证）；dev client 构建与后台静默续传归 M2，且后台续传为加分项非门禁。

**识别端不变量（识别端唯一改动点）**
- 空 `items` 的报告一律 `status = failed`（识别端后处理规则保证 + 数据服务入库校验镜像）；`failed` 报告无可核对项、不计入待核对，出口 = 重新拍照生成新报告，原报告留痕沉底。

**客户端工程**
- 单一前端工程（React + Expo + TypeScript）；选图差异（验证环境文件选择 vs 真机相机/相册）集中在一个 platform 抽象模块；业务页面只依赖 API 封装与该抽象，不散落原生分支。
- Web 仅作验证通道（Expo Go / 模拟器优先，Expo Web 可选辅助），保留长期验证入口；Web 不是产品对外入口，不做第二套业务页面。
- 时间线/详情/上传为 P0 页面；状态文案映射固定为：success→识别完成、partial→待核对、failed→识别失败；条带解析（ref_range 多形态 `'18.40'` / `'<2.00'` / `'70-80'` / null）客户端实现一份、集中放置，画法细则 M1 前 POC 定稿。
- 权限申请文案说明用途为上传检查单；文案中性（停事实侧，不做解读/评分/建议）。

## Testing Decisions

- **好测试只测外部行为**：不测内部实现细节；契约形状由 fixtures 锚定，行为由集成测试锚定。
- **唯一新 seam = HTTP 边界 `/api/v1`**：用 httptest 起 serve 的 handler 栈、以既有编排层 fakes 打底（该 fakes 已被 CLI 测试在用，不在低层新增 seam）。覆盖：同步上传与 SHA256 幂等返回、核对状态机全转移与修正对 append、状态派生单调性、flag 重算、改归属、删除的留痕边界、成员 CRUD 校验、上传 409 拒绝规则。
- **契约锚**：OpenAPI 契约 ↔ HTTP fixtures（golden JSON）；识别端 golden 与 pytest 回路原样保留，本期不动。
- **既有回路复用**：识别服务客户端的 httptest 集成测试、编排层 fakes、契约双向互证测试均为既有 prior art；e2e 全链路标准序列（共享 compose 栈上的 snapshot / refresh / verify 护栏）在「Go 改动」一档扩展为包含 serve HTTP 冒烟。
- **客户端纯逻辑直测**（单元测试）：条带解析模块（多形态 value/ref_range）、离线队列 reducer、状态→文案映射。UI 行为不写单测，由 M1 验证环境门禁（六条用例：配对→当场核对确认+修正；干净直落；任意项修正与徽标同步；改归属；删除后同图可重传；failed 展示原因不计数）与 M2 真机门禁（含相机）覆盖。

## Out of Scope

- **M3–M5**（成员卡片首页、「较上次」Δ 的展示 UI、指标趋势页、筛选/空态完善、iOS+Android 双端回归）——本期签订但非 MVP 门禁；到点另立 spec。注意对应的 **B2-lite*/B2 契约本 MVP 内（M0）即冻结**，避免二次冻结。
- 鉴权与公网部署（ADR-0006：另行立项评审）；删除的回收站（接受硬删）。
- 修正对回流评价工具的**实现**（本期只存可回流形状）。
- 成员删除、生日/头像等成员扩展字段；多成员混单归属。
- 客户端内 OCR/规则抽取/模型推理；医疗解读、评分、用药建议文案。
- Web 作为对外生产入口；微信小程序；双端原生分别维护业务页。
- 医生分享/导出；年龄分段参考范围叠加（与决策 #8「范围一律从检查单抽取」冲突）。
- 跨物理单位换算系数与运行时换算（趋势连接键 = 规范名 + 归一单位，跨单位族点段不连线不提示，留给未来真实需求驱动）。

## Further Notes

- **交付切片与门禁**：M0 契约冻结（OpenAPI + 迁移 + HTTP fixtures，OpenAPI 与 Go/TS 生成物同步为完成判据）→ M1 信任纵切（验证环境六条用例全绿为门禁）→ M2 真机主路径 + 配对（NAS 常驻实例验收）。每个 UI 迭代先验证环境后 App，未过验证门禁不算完成。
- **本 MVP 的成功标准**：家里至少一位非开发者日常真实使用它拍照、归档并核对。
- **关键假设观察点**（M1 后第一个真实使用周期验证，错则降级、不弃船）：家长真的会核对（灵魂假设）；多数核对机会发生在纸还在手边时；成员最小模型撑得起一期。
- 条带画法细则（多形态 value 的点/区间/边界置外）与横滑对照形态是**唯一有意挂起给 M1 前 POC** 的两项，已在 v1.3 文档标注。
- 词典层新增规则或 CLI 变更涉及识别回路时，须按 e2e 文档先内环（pytest + golden + score）再全链路收口。
