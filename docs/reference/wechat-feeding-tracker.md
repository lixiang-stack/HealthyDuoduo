# 微信小程序「喂奶速记」调研：可移植能力与产品边界

Status: **RESEARCH — 部分产品决策已确认**（2026-11-09；2026-11-23 更新）

> **2026-11-23 决策进展：** 用户确认保持 LAN-first / 无账号；统计图表与提醒优先于就诊摘要；产品重心确认 B（日常记录优先），B3 作为最终结构，一级导航确认 **appbar tabs**。原型与截图见 [A/B1](../../.scratch/care-log/prototype/shots/00-contact-sheet.png)、[B2](../../.scratch/care-log/prototype/shots/00-contact-sheet-b2.png)、[B3](../../.scratch/care-log/prototype/shots/00-contact-sheet-b3.png)、[一级导航对比](../../.scratch/care-log/prototype/shots/00-contact-sheet-nav.png)。

范围：调研微信小程序「喂奶速记」的公开信息、可观察功能、同类产品基线与可移植性；结合本仓库的成员、生长记录、报告、分析模型，给出「现在做 / 以后做 / 不做」的分层建议。

> 本文只做调研与产品评估，不修改代码、schema、API 或 UI。§7 的数据模型是建议草案，不是已实现契约；任何落地都需要另开 spec / ADR 并按 [docs/agents/contracts.md](../agents/contracts.md) 同步契约。

**核心判断（先看这里）：** 最值得移植的是「快速记录 + 上次事件 + 今日时间线」的交互原则和喂养事件的数据形状；最不值得移植的是微信账号 / 家庭邀请 / 云同步；本产品真正值得验证的差异化是自建的「就诊摘要」，它不是「喂奶速记」的功能，而是把护理事件接到已验证的医学档案上；不要为了移植而再做一个完整 tracker。**2026-11-23 用户已选择先做统计 / 提醒、就诊摘要后置；这不改变“差异化在就诊摘要”的判断，只改变排序。**

## 1. 决策问题与短答

1. **「喂奶速记」到底是什么产品？**
   它是北京海印未来科技有限公司运营的微信小程序，2019-11-14 注册，服务类目为「工具 / 办公社交 / 笔记」；官方简介把它描述为多人协作的宝宝喂养、便便、尿尿、睡觉、辅食记录工具。公开信息足以确认主体、注册日、类目和一句话定位；正式上线日未证实，2019-12-11 的源码提交只能证明当时已有公开代码快照；不足以确认 2026 年线上 UI、用户规模、留存和商业模式。

2. **它解决的核心用户任务是什么？**
   据品类基线与源码推断：夜间和日常快速回答「上次喂奶几点、吃了多少、谁在照顾」，以及「今天尿了几次、便了几次、睡了多久」。喂养、尿布、照护交接是高频刚需；睡眠、辅食、统计、提醒是次级；内容、社区、商城不是这个产品的核心任务。该排序未经过用户访谈，见 §3.2 与 §7.5。

3. **这些任务与本产品现有模型如何匹配？**
   成员是天然复用点；生长记录可以共享「成员 + 时间」的展示层；报告和分析不应与护理事件混表。护理事件是新的领域概念，数据节奏从「偶发报告」变成「每天多次」，会把产品重心从档案转向日记。LAN-first 支持家庭内多设备共用，但不支持远程邀请、身份、角色和权限。

4. **候选功能如何分层？**
   先验证；验证通过后只做最小喂养事件、今日时间线、「距上次喂养」、修正 / 删除；以后做统计图表、提醒、尿布、睡眠、吸奶、辅食、就诊摘要；不做家庭账号 / 邀请 / 权限、云同步、医疗 / 喂养 / 疫苗建议、内容社区商城、微信小程序克隆。

5. **在「健康育儿」长期定位下，什么才是护城河？**
   不是记录器，而是已核对的检验报告、生长记录、来源可信标记和局域网隐私。护理事件是品类标配，只有接到「就诊摘要」上、把日常上下文与已验证的医学记录连起来，才有差异化。

6. **主要风险是什么？**
   医疗建议边界、儿童健康数据隐私、微信生态与原生 App 的取舍、提醒可靠性、记录疲劳、导出给医生时的误读。均可通过窄范围、来源标注、LAN-only、无建议文案和真人验证来控制。

### 3.2 交互形态：谁记录、记录什么、多人怎么协作

**谁记录。** 源码用微信登录换取 `sessionId`，保存微信头像昵称；记录列表每条带 `userPic`，今日页显示家庭成员头像。宝宝档案里有「我是」选项：妈妈、爸爸、奶奶、爷爷、姥姥、姥爷、叔叔、阿姨、婶婶、舅舅、舅妈。更像是家庭内使用微信的照护者在记录，而不是医院或专业人员的工作流；但具体权限、角色、能否代记，未观察到。

**记录什么。** 源码有五类记录：喂奶（母乳 / 奶粉，可选奶量 ml，开始 / 结束时间）、吸奶（双乳 / 左乳 / 右乳，可选奶量 ml，界面只记一个时刻，数据层仍带默认相同的 begin/end）、换尿布（尿尿 / 便便 / 尿+便，一个时刻）、睡觉（开始 / 结束）、辅食（食物名称必填、可选克数 g，一个时刻，数据层同样带默认相同的 begin/end）。每条记录都有备注；喂奶和吸奶有数量；辅食有食物文本。

**多人怎么协作。** 官方简介说「家人一起共享记录，随时绑定、解绑家人」。源码里可见：邀请页通过微信 `open-type="share"` 分享邀请卡片；被邀请人打开 `invitopen` 页，授权后接受邀请；今日页显示家庭成员头像；记录带记录人头像。解绑、角色、权限、跨家庭隔离未在源码中观察到。

**信息架构。** 两个 tab：「今日」「记录」。今日页是快速记录 + 今日时间线 + 家庭头像 + 最近记录滚动区 + 一句照护提示（如「宝宝喝完奶记得拍嗝哦」）。记录页按天分组，显示每类记录的时间与摘要，可选择起止日期；点某一天进入单日详情，可编辑或长按删除。另有宝宝信息页：乳名、性别、生日、关系、邀请家人、功能模块开关、反馈入口。

**品类基线归纳：**

- **刚需核心：** 喂奶（母乳 / 瓶喂 / 泵奶）、尿布、睡眠、快速记录、上次事件时间、家庭共享、按天回顾。
- **常见扩展：** 生长记录、辅食、提醒、统计图表、PDF / CSV 导出、Widget / 手表 / 语音。
- **差异化扩展：** 专家睡眠 / 喂养建议（Huckleberry）、孕产与内容（Nara）、社区与电商（亲宝宝）。

**结论（推断）：** 「喂奶速记」的功能范围与品类基线高度重合，但没有证据表明它在统计、导出、内容、商城上做了完整建设。它真正的产品优势更可能是「微信内零安装 + 家庭邀请 + 快速记录」，而不是功能深度。这是从分发形态、源码邀请流程和官方简介归纳的推断，不是用户调研结论。

## 5. 移植评估矩阵

> 结论列：**现在做** = 先做用户验证、验证通过后的本轮最小切片；**以后做** = 有验证信号再做；**不做** = 当前架构 / 定位下主动放弃。

| 功能 | 用户任务 | 与现有模型的关系 | 价值 | 成本 / 风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 喂养记录（母乳 / 奶粉，时间、量、备注） | 夜间和日常回答「上次喂奶几点、吃了多少」 | 新增 `feeding_events`；复用成员；不进报告 / 项目组 / 趋势 | 高频刚需；最小切片的核心 | 新表、新 API、新屏幕；字段多会记录疲劳；跨午夜要处理时区 | 现在做 |
| 吸奶记录（左右侧、量） | 母乳妈妈记录泵奶量，估算瓶喂库存 | 与喂养同属「喂养」但语义不同；可后置 | 对混合喂养有价值，但人群较窄 | 增加类型与字段；首版做会稀释最小切片 | 以后做 |
| 尿布记录（尿 / 便 / 混合） | 判断摄入与排泄；就诊时回答「一天几次」 | 新增事件表；复用成员；不进报告 | 新生儿高频刚需；与喂养组成「输入 / 输出」 | 第二个事件类型；需要决定是否共用表 | 以后做（第二切片） |
| 睡眠记录（起止 / 计时） | 了解作息、夜醒、白天小睡 | 新增事件表；复用成员；与生长记录只是同一时间线 | 高频，但更偏作息管理；医生问诊价值低于喂养 / 尿布 | 计时器、跨午夜、编辑体验；容易变成另一个产品 | 以后做 |
| 辅食记录（食物、量、反应） | 6 月龄后记录新食物与过敏反应 | 新增事件表；食物文本；过敏反应是另一层 | 后期刚需；与「健康育儿」自然相关 | 食物库、过敏 / 反应、建议边界；内容运营成本高 | 以后做 |
| 今日时间线 | 一屏看到今天发生了什么 | 读模型：成员 + 事件；不需要新表 | 交接与回顾的核心界面 | 需要新的成员级页面；不要新增全局 tab | 现在做 |
| 距上次喂养 | 夜间不用翻记录，直接看「多久前」 | 从最新喂养事件派生；不存储 | 最小切片里最高的单点价值 | 只陈述事实，不能写成「该喂了」 | 现在做 |
| 按日 / 周统计 | 看趋势、找规律、给医生看 | 读模型；数据量小的时候可不做 | 有用，但品类标配、无差异化 | 图表 / 聚合 / 时区；容易变成低价值仪表盘 | 以后做（第二切片，优先于就诊摘要） |
| 家庭邀请 / 绑定 / 解绑 | 多个照护者共享同一份记录 | 需要身份、角色、权限、跨设备 / 跨网络；与 ADR-0006 冲突 | 对家庭协作价值高 | 账号、鉴权、TLS、审计、儿童数据合规；是架构级变更 | 不做 |
| 记录归属人 | 知道「这条是谁记的」 | 需要身份；当前无账号 | 交接时有用 | 假头像 / 假名字会制造不可信数据；没有身份就不做 | 不做 |
| 提醒（喂奶间隔 / 睡眠） | 到点提醒，减少遗忘 | 原生本地通知；不需要服务端；但需要权限与设备能力 | 品类常见，但可能增加焦虑 | 普通工具类小程序通常只能用一次性订阅（长期订阅仅对特定公共服务开放）；原生也有权限、精确闹钟、厂商省电限制；默认间隔会变成建议 | 以后做（第二切片；可选、本地、用户设定、默认关闭） |
| 就诊摘要 / 导出 | 把最近一段时间的喂养、尿布、睡眠、生长、异常报告带给医生 | 本产品扩展（非喂奶速记功能）；读模型：事件 + 生长 + 报告 + 分析事实层；标注来源；不把解释层当诊断 | 真正的差异化：把日常上下文接到已验证的医学记录 | PDF / 隐私 / 误读；必须区分「家长记录」与「已核对检验值」 | 以后做（统计 / 提醒之后） |
| 宝宝档案 / 关系 | 记录宝宝乳名、性别、生日、我是谁 | 成员已有姓名、性别、出生日期；关系字段没有身份模型支撑 | 对单家庭 LAN 场景价值低 | 重复字段；关系无法可靠归属 | 不做（复用成员） |
| 模块开关 | 隐藏不用的记录类型 | 只有 1–2 类事件时没有意义 | 低 | 增加设置与测试面 | 不做 |
| 多宝宝 / 双胞胎 | 在多个宝宝之间切换 | 成员模型已支持多个成员；事件按 `member_id` 归属 | 现有模型已覆盖，不需要专门功能 | 专门 UI 会分散首版注意力 | 不做（现有成员即可） |
| 内容 / 社区 / 商城 | 育儿知识、家长交流、商品 | 完全独立的内容 / 电商域 | 对活跃与商业化有价值，但不是本产品优势 | 内容审核、医学审核、运营、供应链；与「档案」定位冲突 | 不做 |
| 疫苗 / 用药提醒 | 按免疫程序提醒接种；按医嘱提醒用药 | 需要官方免疫程序、年龄计算、补种规则、禁忌症；用药需要医嘱 | 家长有需求 | 医疗 / 健康建议边界；官方程序会更新；错误提醒有实际伤害风险 | 不做 |
| 生长曲线 / 百分位 | 看身高体重是否在正常范围 | 生长记录已有；百分位需要标准与年龄性别 | 与现有生长记录自然衔接 | 医学标准选择、版本、解读文案；不是「喂奶速记」的能力 | 以后做（独立评审，不从本产品移植） |

**矩阵读法：**

- 「现在做」只有三组：喂养记录（含修正 / 删除）、今日时间线、距上次喂养。它们构成一个能独立验证的最小闭环；验证通过才写代码。
- 「以后做」的共同前提是：最小闭环被真实家庭使用，且「就诊摘要」被医生 / 家长认为有用。
- 「不做」的共同理由是：需要身份 / 云 / 内容 / 医学审核，或会改变产品重心，而不是「技术上做不到」。
- **2026-11-23 用户确认：统计图表 / 提醒提前到第二切片，就诊摘要后置；产品重心待 A/B 原型选择。**

**三类判断：**

| 类型 | 功能 | 判断 |
| --- | --- | --- |
| 同一用户旅程的自然延伸 | 喂养、尿布、睡眠、辅食、今日时间线、距上次事件 | 复用成员与时间线；可以按需加，但要控制类型数量 |
| 会改变产品重心 | 统计图表、提醒、今日页成为首页、内容 / 建议 | 不是不能做，而是会把「档案」变成「日记」；需要单独的产品决策 |
| 会突破架构边界 | 家庭账号 / 邀请 / 权限、云同步、远程推送、医学建议 | 与 ADR-0006 或产品边界冲突；需要新 ADR / 合规评审，不是功能迭代 |

**关于 care event 领域概念：** 概念上承认「日常护理事件」是与「检查报告」不同的领域；但首版不做通用 `CareEvent` 抽象或宽表。先用 `feeding_events` 把一条竖切跑通，等第二种事件类型（尿布）真实落地，再决定是扩表、建子类型还是提炼共同接口。这样避免为未发生的类型设计一张充满可空字段的多态表。

### 6.1 品类标配与护城河

| 能力 | 品类属性 | 是否值得自建 | 理由 |
| --- | --- | --- | --- |
| 快速记录 / 上次事件 | 标配，但决定体验 | 值得，做薄 | 这是用户打开产品的第一理由；不需要复杂功能，只需要快和准 |
| 家庭共享 | 标配 | 不自建完整版 | 同 LAN 多设备已能共享；账号 / 邀请 / 权限是架构级成本 |
| 统计图表 | 标配 | 不自建早期 | 同质化、低差异化；数据量小的时候价值更低 |
| 提醒 | 标配 | 不自建早期 | 可靠性受平台限制；默认间隔会变成建议；先做「距上次」事实展示 |
| 内容 / 育儿建议 | 部分产品的差异化 | 不自建 | 需要医学审核、内容运营与持续更新；不是本产品优势 |
| 社区 / 商城 | 亲宝宝等平台的差异化 | 不自建 | 供应链、运营、审核；与「家庭健康档案」定位冲突 |
| 报告 OCR / 核对 / 趋势 / 分析 | 本产品已有 | 继续做深 | 这是本产品的核心资产；护理事件无法替代 |
| 就诊摘要 | 潜在差异化 | 以后做（统计 / 提醒之后） | 把日常上下文与已验证的医学记录连起来；竞品少有人做「来源可信」的摘要 |
| 来源可信 / 隐私 | 本产品差异化 | 继续做深 | 检验值有核对与信任标记；护理事件标「家长记录」；LAN-only 是隐私卖点 |

**判断：** 记录器、家庭共享、统计、提醒、内容、社区、商城都是别人的标配或别人的护城河；本产品不该在这些方向上和人拼功能完整度。真正值得投入的是「已验证的纵向医学档案 + 日常上下文 + 来源可信 + 隐私」，而就诊摘要是把这些串起来的用户可见产物。

| 偏离点 | 喂奶速记的做法 | 本产品的选择 | 理由 |
| --- | --- | --- | --- |
| 平台与分发 | 微信小程序；微信内搜索 / 分享；零安装 | 原生 Expo / React Native App；LAN 内扫码配对 | ADR-0006、ADR-0013；不为一个记录功能复制一个小程序产品。 |
| 身份与协作 | 微信登录；邀请家人；共享宝宝；绑定 / 解绑 | 无账号；单家庭；同一 LAN 多设备可直接读写；不做邀请 / 角色 / 权限 | 身份会带来鉴权、TLS、审计、儿童数据合规；是架构级变更，不是功能级变更。 |
| 数据重心 | 高频护理日志；今日页是首页 | 检查报告档案 + 生长记录 + 分析仍是核心；护理事件是成员级附属 | 避免把产品从「可信档案」变成「又一个育儿记录器」。 |
| 数据可信 | 记录是家人自报；没有检验值那样的核对 / 信任标记 | 检验值保留核对与信任标记；护理事件明确标「家长记录」，不与检验值混排 | 「数字可信」是本产品差异点；自报数据不能伪装成已验证数据。 |
| 建议边界 | 工具记录 + 照护提示；运营站点称支持提醒 | 不做诊断、治疗、复查、喂养量、睡眠训练、疫苗建议；只做事实汇总与「和医生讨论」 | 与现有产品边界一致；医学内容需要审核与来源版本。 |
| 商业化 | 未观察到付费 / 广告 / 商城 | 不做内容 / 社区 / 商城 | 不是本产品优势；会引入内容审核与供应链负担。 |
| 提醒 | 运营站点称支持；机制未证实 | 首版不做；以后只做用户设定、默认关闭、本地通知的中性计时 | 微信订阅消息不能支撑高频间隔提醒；原生提醒也有系统限制；默认间隔会变成建议。 |
| 范围 | 五类记录 + 家庭协作 | 首版只做喂养事件 + 今日时间线 + 距上次喂养 | 最小验证；避免记录疲劳与产品重心漂移。 |

> 落地时，§6.2 的每一行都应回到 spec 的「非目标 / 风险 / 验收」，不要只留在调研文档里。

## 7. 建议路线

### 7.1 最小一步

**最小一步分两层：先验证，再写代码。**

**验证层（不写生产代码）：** 用纸面或可点击原型，找 5–8 个新生儿家庭和 3 位儿科 / 儿保医生，验证两个假设：夜间喂养回忆是否值得打开一个 LAN 原生 App；就诊摘要是否值得带给医生。验证不通过，就不进入代码层。前端方案按 [prototype-driven-development.md](../agents/prototype-driven-development.md) 先出可运行原型 + 目标尺寸截图，再选型实现。

**代码层（验证通过后）：只做「喂养事件」这一条竖切：**

1. 从成员卡进入成员级「今天」页；不新增全局 tab。
2. 一键记录：类型（母乳 / 奶粉）、开始时间（默认现在）、结束时间（可选）、奶量（可选）、备注（可选）。
3. 今日时间线：当天喂养事件按时间排列；顶部显示「距上次喂养 2 小时 15 分」这类事实，不写「该喂了」。
4. 修正 / 删除：点事件进入编辑；删除需确认。
5. 数据只走现有 LAN 后端；不做云同步、不做家庭邀请、不做提醒、不做统计图表。

**为什么不是「尿布 + 睡眠 + 统计」一起做：** 每多一个类型，就多一套字段、空状态、编辑路径和测试面；首版要验证的是「家长会不会在 LAN 原生 App 里记录喂养」，而不是「能不能做一个完整 tracker」。**按 2026-11-23 决策，统计 / 提醒紧随喂养切片；就诊摘要后置。**

### 7.2 数据模型最小改动

> 建议草案，不是已实现契约。首版不建通用 `care_events` 宽表，也不建 `CareEvent` 接口 / 抽象；只建 `feeding_events`，等第二种事件类型真实落地再决定是否抽象。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `bigserial` | 是 | 主键 |
| `member_id` | `bigint` | 是 | 外键 `members(id)`；成员删除时级联删除 |
| `method` | `text` | 是 | `breast` / `formula`；用枚举约束 |
| `started_at` | `timestamptz` | 是 | 开始时间；存绝对时间，展示按家庭本地时区 |
| `ended_at` | `timestamptz` | 否 | 结束时间；母乳可计时，奶粉可只记时刻 |
| `amount_ml` | `double precision` | 否 | 瓶喂 / 奶粉奶量；母乳亲喂可不填 |
| `note` | `text` | 否 | 备注 |
| `created_at` | `timestamptz` | 是 | 创建时间，默认 `now()` |

**约束与索引：**

- `amount_ml > 0`；`ended_at is null or ended_at >= started_at`。
- `method in ('breast','formula')`。
- 索引 `(member_id, started_at desc)`，用于「最近一次」和按日查询。
- 不存 `recorded_by`、`device_id`、`trust_mark`：没有身份模型，不要制造假归属；护理事件是自报，不能复用检验值的信任标记。
- 不把喂养事件写进 `reports` / `report_items` / `trends` / `analysis`；它们不是报告，也不是指标趋势。
- 成员删除时清理 `feeding_events`：与现有 `growth_records` 的 `ON DELETE CASCADE` 一致；报告走 ADR-0014 的显式删除。实现时补成员删除测试。
- 跨午夜用 `timestamptz` + 客户端本地日分组；不要用 `date` 字段把 23:50 和 00:10 粗暴分到两天而不保留绝对时间。

### 7.3 API / UI 最小面

- `POST /members/{member_id}/feeding-events`：创建。
- `GET /members/{member_id}/feeding-events?from=YYYY-MM-DD&to=YYYY-MM-DD`：按范围列出，倒序。
- `PATCH /feeding-events/{id}`：修正时间 / 类型 / 量 / 备注。
- `DELETE /feeding-events/{id}`：删除。
- 路径命名按现有 OpenAPI 风格调整；这里只表达资源关系，不是已冻结契约。
- 「距上次喂养」由客户端从最新一条派生，不新增服务端字段；不需要统计接口。
- UI 只加一个成员级「今天」入口；空状态写「今天还没有记录」，不写催促或评价。
- 事件卡片标「家长记录」，与报告卡片的时间 / 来源 / 信任标记区分。

### 7.4 明确不做

- 不做微信小程序版本；不为一个记录功能引入第二套客户端与契约。
- 不做家庭账号、邀请、绑定 / 解绑、角色、权限、跨家庭隔离。
- 不做云同步、远程推送、跨公网访问；如要做，先按 ADR-0006 重新评审鉴权、TLS、审计与儿童数据合规。
- 不做喂养量 / 间隔建议、睡眠训练、疫苗提醒、用药提醒、诊断 / 治疗 / 复查建议。
- 不做内容、社区、商城、排行榜、打卡 streak。
- 首版不做完整统计图表与 PDF 导出；统计图表在第二切片做（2026-11-23 决策），PDF 导出仍后置。多宝宝专属 UI、模块开关不做。
- 首版不记录左右侧、奶粉品牌、剩余奶量、喂养姿势；这些字段没有验证过，先不加。
- 不把护理事件塞进报告趋势或分析快照；就诊摘要如果以后做，单独设计读模型与来源标注。
- 就诊摘要只带事实层、已核对指标和原始报告引用；解释层留在 App 内给家长看，不写成诊断结论。

### 7.5 验证计划

> 阈值是建议值，需产品确认；目的不是「跑通功能」，而是决定要不要继续投入。

| 假设 | 方法 | 通过标准 | 失败后的动作 |
| --- | --- | --- | --- |
| 家长愿意在 LAN 原生 App 里记录喂养，而不是继续用纸 / 微信 / 记忆 | 5–8 个新生儿家庭，2 周；记录使用日志 + 访谈 | ≥ 70% 的天数至少有 1 条喂养记录；记录耗时中位数 ≤ 5 秒；2 周后 ≥ 50% 家庭仍在使用 | 停在原型；不投入尿布 / 睡眠；重新评估「就诊摘要」是否需要护理事件 |
| 「距上次喂养」是夜间最高价值信息 | 访谈 + 页面使用日志 | ≥ 50% 的夜间使用会打开「距上次喂养」；家长能用自己的话说明它解决了什么 | 价值可能在交接或尿布；调整最小切片，不急着加统计 |
| 统计图表会被用来回顾，而不是只看一次 | 5–8 个家庭，2 周；页面访问日志 + 访谈 | ≥ 50% 家庭每周至少打开 2 次统计；能说出一个具体用途 | 只保留「距上次」和今日摘要，不做完整 dashboard |
| 家庭协作的真实需求是「远程家人」而不是「同屋多设备」 | 访谈；观察现有 LAN 多设备使用 | 有远程照护者的家庭 ≥ 30%，且愿意接受账号 / 云 / 隐私权衡 | 保持 LAN-only；不做邀请 / 账号 |
| 就诊摘要值得做 | 用原型 PDF 给 3 位儿科 / 儿保医生和 5 位家长看 | ≥ 3/5 家长愿意下次就诊带上；≥ 2/3 医生认为比口述 / 手机相册更有用 | 护理事件只做家庭自用，不投入摘要 |
| 提醒不会增加焦虑 | 可选原型；记录开启率、关闭率、夜间查看次数、访谈 | 用户描述「被提醒」而非「被催促」；没有明显增加夜间检查 | 不做提醒；保留纯事实的「距上次」 |

### 7.6 分阶段门槛

| 阶段 | 内容 | 进入下一阶段的门槛 |
| --- | --- | --- |
| 0. 验证 | 访谈 + 纸面 / 可点击原型；不写生产代码 | 至少 3 个家庭明确说「愿意用」，且能说清使用场景 |
| 1. 喂养最小切片 | `feeding_events` + 今日时间线 + 距上次 + 修正 / 删除 | §7.5 前两条通过；RNTL + Android 真机 smoke 通过 |
| 2. 统计 / 提醒 + 尿布 | 基础统计图表、本机提醒、第二类事件；就诊摘要后置 | 统计 / 提醒有真实使用；尿布需求成立；来源标注与隐私评审通过 |
| 3. 睡眠 / 吸奶 / 辅食 / 就诊摘要 | 按真实需求逐个加；就诊摘要只在统计 / 提醒有信号后做 | 每个类型都有独立需求证据；就诊摘要被医生 / 家长认为有用 |

## 8. 风险与待验证

### 8.1 风险表

| 风险 | 触发条件 | 影响 | 缓解 / 决策 |
| --- | --- | --- | --- |
| 医疗建议边界 | 写「该喂了」「每次喂 X ml」「睡训」「疫苗该打了」 | 被理解为医疗 / 健康建议；合规与信任风险 | 只做事实记录与「和医生讨论」；不做默认间隔、剂量、诊断、治疗；医学内容另走审核与来源版本，必要时评估是否构成医疗器械软件 |
| 隐私与云同步 | 引入账号、家庭邀请、云同步、远程推送 | 儿童健康数据成为敏感个人信息；需要单独同意、监护人同意、专门规则、加密、删除机制 | 保持 LAN-only、无账号；如要改，先按 ADR-0006 重新评审，并做 PIPL / 儿童个人信息合规评估 |
| 微信生态 vs 原生 App | 为了复刻「零安装 + 微信邀请」而做小程序 | 第二套客户端、第二套契约、审核与运营成本；与 native-only 验收冲突 | 不做小程序；把「隐私 + 家庭内网」作为差异化，而不是和微信比分发 |
| 提醒可靠性 | 承诺「准时提醒」 | 微信订阅消息需用户点击、长期订阅不对普通工具开放；原生有权限、精确闹钟、厂商省电限制 | 不承诺准时；只做本地、可选、用户设定、默认关闭；真机实测后再上线 |
| 记录疲劳 | 字段太多、类型太多、默认值不合理 | 家长记几次就放弃；数据不完整比没有更糟 | 默认现在、字段可选、先记后改、一屏一键；首版只做喂养 |
| 导出给医生时误读 | 把家长自报的喂养 / 睡眠与检验值混在一起，未标来源 | 医生误把自报数据当测量值；家长误把摘要当诊断 | 来源标注「家长记录 / 实测 / 检验报告」；摘要写「不是诊断」；由用户选择导出范围 |
| 产品重心漂移 | 今日页变成首页，报告 / 分析被边缘化 | 失去「数字可信」的差异点，进入红海 tracker 竞争 | 不新增全局 tab；成员级入口；成功指标是「就诊摘要是否有用」，不是 DAU |
| 证据不足 | 把 2019 源码快照当成 2026 线上；把同类功能当成目标产品功能 | 结论过度自信；做错功能 | 明确证据等级；先做用户验证；不引用不可访问的页面 |

### 8.2 真实用户验证缺口

- **没有真实用户数据。** 不知道家长是否愿意在 LAN 原生 App 里记录，而不是用纸、微信或记忆。
- **没有医生样本。** 不知道儿科 / 儿保医生是否认为喂养 / 尿布 / 睡眠摘要有用，也不知道他们希望看到什么粒度。
- **没有线上 UI。** 不知道「喂奶速记」2026 年的实际交互、提醒机制、家庭协作权限。
- **没有合规评审。** 儿童健康数据、医疗建议边界、疫苗提醒都需要法务 / 医学 / 合规复核；本文不是法律意见。
- **没有提醒实测。** 微信订阅消息与原生本地通知的真实到达率、夜间打扰、家长焦虑都需要真机 / 真人测试。

## 10. 产品决定与偏离

### 10.1 本文的调研结论（可被证据支持）

1. 「喂奶速记」是一个以微信为分发、以家庭共享为差异点的轻量护理记录工具；公开信息不足以证明它在统计、提醒、导出、内容上做了深度建设。
2. 它的可移植价值主要在**数据形状**（喂养 / 尿布 / 睡眠 / 辅食的字段与时间语义）和**交互原则**（默认现在、字段可选、先记后改、今日时间线、上次事件、交接）。
3. 它的家庭协作依赖微信身份与云端；这与本产品 LAN-first、无账号、单家庭的边界冲突，不能直接移植。
4. 护理事件与检查报告是两种数据节奏、两种信任来源；可以共享成员与时间线展示，不能共享表、趋势或分析快照。
5. 在「健康育儿」长期定位下，护理事件是标配，检验报告 + 生长 + 分析 + 来源可信才是护城河；护理事件只有接到「就诊摘要」上才有差异化（就诊摘要是本产品自建扩展，不是「喂奶速记」已证实的功能）。

### 10.2 建议的产品选择（部分已确认）

以下 10 条是本文的建议；标「已确认」的为 2026-11-23 用户决定，其余待确认。§10.4 列出已确认与待确认项。

1. **首版只做喂养事件**，不做完整 tracker；用最小切片验证「家长是否愿意在 LAN 原生 App 里记录」。
2. **不新增全局 tab；从成员卡进入成员级「今天」页，保持「家庭 / 档案」双 tab 的信息架构**（这是 A 方案；若选 B，则今天页成为首页、统计成为一级 tab，见原型）。
3. **不做家庭账号 / 邀请 / 绑定 / 权限**（已确认，2026-11-23）；同一 LAN 多设备已经能共享后端数据，缺的是身份而不是记录同步。
4. **不做云同步 / 远程推送**（已确认，2026-11-23）；如未来要做，先按 ADR-0006 重新评审，并做儿童个人信息合规评估。
5. **不做医疗 / 喂养 / 睡眠 / 疫苗 / 用药建议**；只做事实汇总和「和医生讨论」。
6. **护理事件标「家长记录」，不复用检验值的信任标记**；自报数据不伪装成已验证数据。
7. **不做内容 / 社区 / 商城 / 打卡**；这些不是本产品优势，且会引入内容审核与运营负担。
8. **统计图表 / 提醒先做，就诊摘要后置**（已确认，2026-11-23）；先把品类标配补齐，再验证就诊摘要这个差异化输出。
9. **不照搬「一张 record 表 + recordType + 可空 quantity/info」的多态设计**；首版用 `feeding_events` 明确字段，等第二种事件类型出现再决定抽象。
10. **不把「喂奶速记」当竞品对标**；它证明品类需求存在，不证明我们应该做同样的产品。

### 10.3 什么会改变这些决定

- 真实用户验证显示：家长每天多次打开本产品记录喂养，且「距上次喂养」是夜间核心动作；则可以把喂养从「附属」提升为一级入口。
- 统计 / 提醒的真实使用信号成立（每周多次打开统计、提醒不被关闭）；则值得继续做尿布、睡眠与就诊摘要。
- 医生样本显示：就诊摘要确实需要护理事件；则值得投入尿布、睡眠、摘要，甚至考虑与医院 / 儿保合作。
- 家庭协作的真实需求集中在远程祖辈 / 月嫂；则必须重新评审账号、云、权限与儿童数据合规，而不是偷偷加一个邀请码。
- 医学 / 法务评审认为「中性计时 + 用户设定提醒」仍构成建议；则连提醒也不做，只保留事实展示。

### 10.4 已确认与待确认

1. **产品重心（已确认，2026-11-23）：** 选 B（日常记录优先），最终结构为 B3：appbar 一级域「日常 / 健康档案」，底部二级视图「今天 / 统计」或「报告 / 趋势」。
2. **协作边界（已确认，2026-11-23）：** 坚持 LAN-first / 无账号；不做家庭邀请、云同步、远程推送。
3. **差异化路径（已确认，2026-11-23）：** 先做统计图表 / 提醒等品类标配；就诊摘要后置。

> 本文的原始建议是：**先做喂养最小切片，用真实家庭验证；把「就诊摘要」作为是否继续扩展护理事件的决策门；不把微信小程序的产品形态搬进本产品。** 2026-11-23 用户调整了排序：**统计 / 提醒先做，就诊摘要后置；产品重心确认 B，最终结构为 B3 + appbar tabs。**

## 11. B 方案导航细化（2026-11-23 追加）

> 决策已落 `docs/adr/0019-care-log-navigation-child-context.md`；实现 spec 在 `.scratch/care-log/spec.md`。

用户倾向 B（日常记录优先），并追问：默认打开是否今天页？是否把「今天 / 统计」放到下方导航，进入日常后不再出现健康档案？

### 11.1 两个变体

| 变体 | 一级域 | 二级视图 | 特点 |
| --- | --- | --- | --- |
| B2 | 底部固定「日常 / 健康档案」 | 日常顶部「今天 / 统计」 | 域切换最快；高频视图在顶部 |
| B3 | appbar「日常 / 健康档案」 | 日常底部「今天 / 统计」；健康档案底部「报告 / 趋势」 | 高频视图在底部；进入日常后底部不再出现健康档案 |

原型：`prototype.html` 顶部切换 B2 / B3；截图见 [B2 contact sheet](../../.scratch/care-log/prototype/shots/00-contact-sheet-b2.png) 与 [B3 contact sheet](../../.scratch/care-log/prototype/shots/00-contact-sheet-b3.png)。

### 11.2 建议

- **如果真实使用是每天多次记录，B3 更顺**：高频的「今天 / 统计」放在拇指最容易到的底部；低频的「日常 / 健康档案」放 appbar。
- **健康档案不删除**：本文把「不再出现健康档案页面」解释为「不在日常的底部导航里」，而不是从产品移除；B3 在 appbar 保留一级域入口和待核对小圆点。
- **默认入口**：默认「日常 > 今天」；首次启动可以让家长选「记录今天 / 查看健康档案」；之后记住上次所在的域。
- **命名**：一级域用「日常」而不是「喂养」，因为后续还有尿布、睡眠、辅食；「喂养」只是日常里的一个动作。
- **层级**：最多两层（域 → 视图）；「记录」是动作，不是 tab；不要再加第三层。
- **B3 统计页**：已接入统计图表小原型的指标（喂养 / 奶量 / 睡眠 / 尿布）× 图表类型（柱状 / 堆叠 / 折线）切换；A / B1 / B2 仍保留旧柱状图作为对照。
- **多照护者同一孩子**：孩子上下文必须显式可见；单孩子自动选中，多孩子每台设备选择并记住；记录弹层写「记录给 X」；不做全局 active child，不做账号 / 记录人归属。
- **一级导航呈现（已确认，2026-11-23）**：B3 采用 **appbar tabs**——把「日常 / 健康档案」嵌进 appbar，省 46px，两个域仍一眼可见，一次点击切换。顶部独立 segmented 作为保守 fallback；标题下拉只在 appbar 放不下时用；首页双卡只在做家庭首页时用。对比见 [一级导航呈现原型](../../.scratch/care-log/prototype/shots/00-contact-sheet-nav.png)。
- **代价**：B3 的底部 tab 会随域变化（日常：今天/统计；健康档案：报告/趋势），需要明确「当前域」和返回规则；点当前域时回到该域的根视图。

### 11.3 待确认

1. **B2 还是 B3？** 已确认 B3（2026-11-23），一级导航采用 appbar tabs。
2. 默认入口：固定「日常 > 今天」，还是首次启动选择 / 记住上次域？
3. 一级域名：「日常」是否成立，还是用「护理」「养育」？
4. **提醒是否独立成 tab？** 本文建议暂不：当前提醒只是一个开关 + 间隔，属于设置而非日常视图；先保留今天页卡片 + 设置入口。等出现多种提醒类型、提醒计划或提醒历史，再升级为独立入口。
5. **统计图表类型？** 本文建议先保留柱状图；下一步优先堆叠柱状图表达构成（睡眠夜间/白天、尿布尿/便、母乳/奶粉），30 天趋势再加折线；直方图只用于「间隔 / 单次奶量」的分布，不用于每日总量。三种图的对比见 [统计图表小原型](../../.scratch/care-log/prototype/shots/00-contact-sheet-charts.png)。
6. **一级导航呈现？** 已确认 appbar tabs（2026-11-23）；顶部独立 segmented 作为 fallback，标题下拉 / 首页双卡不采用。见 [一级导航呈现原型](../../.scratch/care-log/prototype/shots/00-contact-sheet-nav.png)。
7. **多照护者如何确认同一孩子？** 建议 B + 显式孩子上下文：单孩子自动选中，多孩子每台设备选择并记住；appbar、hero、记录弹层都显示孩子名；记录弹层写「记录给 X」；不做全局 active child。
