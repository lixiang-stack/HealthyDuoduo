# Research

外部标准 / 法规 / 医学 / 厂商文档等多来源调研的本地约定。代码库内的事实用探索 / 直接读，不走这里。

## 什么时候用

- 需要多个一手来源才能回答：法规、卫生行业标准、临床共识、供应商 API、跨仓库行为。
- 结论会改变 spec / ADR / 契约，且需要可追溯的引用。
- 单一文件、单一网页、单个函数能回答的，直接读；不要为它开调研。

## 步骤

1. **先写成决策问题。** 不是「查一下肝功能」，而是「哪些官方文档支持把肝功作为独立项目组；哪些项必须归入；哪些是我们的产品决定」。决策问题决定要查什么、查到什么程度算够。
2. **先一手来源。** 国家卫健委 / 标准号 / 期刊 DOI / 厂商官方文档优先；二手解读只用来找线索，不作为引用。官方站点超时是常态：用搜索摘要定位标准号，再用第二来源核实，记录访问日期。
3. **派 `research` skill 或 general subagent。** 不要让主上下文吞原始搜索页；要求它返回摘要 + 引用表。主 agent 只负责写 spec。
4. **引用表固定四列：** 文档 | 它定义了什么 | 它**不能**推出什么 | URL / DOI / 访问日期。第四列比第二列更重要：大多数「官方文档」只定义类别或项目名，不定义你的产品分类。
5. **分层结论。** 官方文件 / 专家共识 / 临床惯例 / 产品决定四层分开写；产品偏离单独列出，不要藏在「依据」里。示例：AFP 在 WS/T 645.2 中与肿瘤标志物同组，本产品首版归肝功，是产品决定。
6. **写成 reference。** 可复用的主题放 `docs/reference/<topic>.md`；一次性 spec 调研可以放 spec 附录（如 `.scratch/panel-browse/spec.md` §5.5）。只把决策相关的摘要写进 spec，不要把整页搜索结果粘进去。
7. **标证据边界。** 样本量、是否有真实用户数据、标准版本 / 实施日期、哪些是假设。医学 / 法规结论需要人工复核（`ready-for-human`），不要让 agent 自签。

## 输出检查

- 每个结论都能追到一条引用；没有引用的写成「产品决定」或「待验证」。
- 引用表里至少有一行说明「它不能推出什么」。
- 产品偏离有独立段落，且回流到 spec 的非目标 / 风险 / 验收。
- 调研文件本身能被 `scripts/check-docs.py` 检查通过。

## 已落地示例

- 项目组医学依据：`.scratch/panel-browse/spec.md` §5.5（2026-10-27）。它把「官方基本类别 / 项目名称与代码 / 参考区间 / panel 概念 / 产品决定」分层，记录了 AFP 归肝功的偏离，并把临床复核列为人工门禁。
