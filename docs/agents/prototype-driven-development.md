# Prototype-Driven Development（前端方案选型）

**触发：** 前端页面、信息架构、导航、视觉风格、交互流程存在多个合理方案，或用户需要“先看到”才能判断时。

**目标：** 在写生产代码前，用可运行、可点击、按目标设备尺寸渲染的原型完成选型；不以文字描述或 ASCII 线框代替视觉判断。

## 交付物

放在 `.scratch/<feature>/prototype/`：

```text
prototype.html          # 自包含 HTML/CSS/JS，无构建步骤
shots/
  00-contact-sheet.png  # 所有方案 / 状态的联系表
  01-<variant>.png      # 目标设备尺寸的整页截图
  ...
```

- `prototype.html` 必须能直接用浏览器打开；不引入生产依赖，不接后端。
- 至少 2 个方案并排或可切换；每个方案标注要验证的决策（如“双 Tab vs 单列表”）。
- 使用真实样本数据（优先 `samples/expected/` 或真实脱敏数据），覆盖空态 / 失败 / 长名称 / 异常值等关键状态。
- 截图必须来自实际渲染结果，宽度取目标设备（App 默认 390px）；提供 contact sheet 方便一眼比较。

## 步骤

1. **写清决策**：本次要选什么？每个方案的核心差异是什么？不把多个无关决策混在一个原型里。
2. **搭原型**：HTML/CSS/JS 快速实现；状态用 query string / 按钮切换；方案用并排或开关切换。
3. **渲染截图**：按目标视口截整页；每个方案至少一张；关键弹层 / 空态单独截。
4. **Present**：contact sheet + 每个方案的取舍 + 推荐；明确指出“需要用户判断什么”。
5. **记录选择**：用户选定后写入 spec 决策记录 / ADR；只有这时才进入生产实现。
6. **实现对齐**：生产页面完成后，用同一视口截图对照原型；视觉差异要么修正，要么记录原因。

## 质量底线

- **所见即所得**：截图与 `prototype.html` 一致；不用示意图冒充渲染结果。
- **可点击**：关键路径（进入详情、切换 Tab、打开弹层）在原型里能点通。
- **真实数据**：不用 `Lorem ipsum` 或虚构医学结论；数据不足时标注“样例”。
- **一次只选一个层级**：布局 / 导航 / 视觉分开选，避免原型过大。
- **原型是丢弃物**：不把原型代码直接搬进 App；生产实现遵循现有设计系统与组件。

如果技术选型会影响交互或观感（如动画库、图表库、地图），在候选栈里跑最小关键交互验证；纯信息架构 / 视觉选型用 HTML 原型即可。
