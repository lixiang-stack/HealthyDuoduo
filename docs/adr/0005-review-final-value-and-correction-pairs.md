# 0005 · 核对落库数据模型：items 装最终生效值 + append-only 修正对 + flag 派生

**状态：** 采纳（2026-10-13，需求拷问会定稿）。

家长核对（确认/修正）落库采用「**单真源 + 审计留痕**」：`report_items` 永远装**最终生效值**（家长改了以家长为准），修正历史进 append-only **修正对**表（before→after 全集 + `raw_text` + OCR 行号 + 时间；本期只存不回流，形状按可回流设计，供未来直接喂 `gt_eval`）；`flag` 一律由服务端按修正后的 value × ref_range 重算，**不接受手改**。

## 背景

B3 核对闭环（需求文档 5.2）要求家长对低置信指标项确认或修正。两个设计点各有真实分岔：

1. **「原值」与「最终值」谁是真源**：原需求文档写「修正按可回流形状记录（原值→修正值……）」但未写明下游（时间线/详情/趋势/B2）读哪个值。
2. **flag 手改还是派生**：原需求文档允许修正 value/flag/名称；但 `report.schema.json` 自身定义 flag = 「数值与参考范围比较结果」——纯函数。

## Considered Options

- **items 装原值 + 读取时 join 修正对算「应显示什么」**：每个消费点（时间线/详情/趋势/B2/成员卡片）都要叠加同一层逻辑，漏一处就是「档案里显示 OCR 错值」——直接违反「屏幕上的数字可信」的产品灵魂。否。
- **flag 手改**：会出现 flag=normal 但值明明白在范围外的档案，时间线徽标（按 flag 聚合）与详情条带染色直接打架。否——修正 flag 的正确动作是修正 value 或 ref_range；「纸上印 ↑ 而范围解析失败」的场景，家长照纸补 ref_range，flag 自然算出（与决策 #8「范围一律从检查单抽取」同源）。
- **允许「撤销核对」**：决策只追加不删除即可保证报告状态派生单调（partial→success 单向）；误确认的出口是「修正」，语义已覆盖，撤销是多余机制。否。

## Consequences

- 下游查询零 join、零分支，核对结果全端即时一致。
- 决策可重复（每次修正 append 一条，最终状态 = 最后一次动作）、无撤销、报告状态派生单调——B3 天然幂等，离线补传核对结果安全。
- 确认不产生修正对记录；只有修正才记。
- 修正对表按可回流形状落库（本期只存不回流），未来回流 `gt_eval` 零迁移。
- `unreviewed_low_confidence_count` 为响应派生值（不落列）：只统计 `partial` 报告中未处理的低置信项；`failed`（含空 `items` ⇒ `failed` 的识别端不变量）不计数。
