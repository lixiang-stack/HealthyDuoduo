# 0010 · 多图上传 = 多份独立报告，客户端串行单图上传

**状态：** 采纳（2026-10-24，需求拷问会定稿）。

一次上传动作允许选择最多 9 张图像；**每张图仍独立识别、独立归档为一份报告**，不合并成一份多页报告。传输上不新增批量接口：App 按选择顺序**串行**调用现有单图 `POST /reports`，每张图一个 multipart 请求；单张失败不阻断后续，结果逐行呈现，只重试传输失败项。

## 背景

- 现状 App 只取 `assets[0]`，契约明确「单图,对应一张检查单」；报告主键是图像 sha256（`reports.image_sha256`），`CONTEXT.md` 定义图像 ↔ 检查单 1:1、报告是查询基本单位。
- 家长一次面对多张检查单时逐张拍照 / 选择、逐张上传，交互成本高；需求是「单次多张上传识别」，不是「多页合并」。
- 识别服务同步、CPU 推理，RapidOCR 引擎是进程级单例；后端识别客户端 60s 超时 + 1 次重试。

## Considered Options

- **多页合并为一份报告**：需要改变报告身份（不能是单图 sha）、跨页指标合并、日期冲突处理，属于独立领域模型变更；本期不做。
- **后端批量接口 `POST /reports/batch` / `images[]`**：每张图本来就是独立归档，批量接口没有事务收益，却要把部分失败、超时、请求体上限、重试语义搬进后端；App 是唯一客户端。否。
- **客户端 fan-out（串行单图请求）**：复用现有契约、sha 幂等、全部测试；部分失败天然按张隔离。采纳。

## Consequences

- OpenAPI / Go / 识别服务 / 数据库零改动；不新增「批次」领域实体，`CONTEXT.md` 不变。
- 一次 N 张 = N 个请求、N 份报告、N 条独立结果；单张失败不影响其他张。
- 上限 9 张；相册多选 + 拍照逐张追加；整批同一成员，传错可在报告详情改归属。
- 单张上传增加 180s 超时（覆盖后端 60s × 2），超时记为失败可重试。
- 上传中离开页面：请求继续、报告照常归档，批次状态不持久化；不做断点续传。
- 多页单张检查单仍是未支持场景；若出现真实需求，另立 ADR / spec，重新评审报告身份与合并规则。
