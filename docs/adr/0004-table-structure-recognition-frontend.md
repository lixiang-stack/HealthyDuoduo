# 0004 · 表格类报告引入表格结构识别（TSR）前端：选 TableStructureRec

**状态：** 已评估，**不采用**（2026-10-11）。曾按本 ADR 落地 TSR 网格抽取，但基于真实数据对照（`samples/expected/vl`）实测，**TSR 网格抽取显著劣于启发式**，故已回退网格相关代码，仅保留原型（`tools/tsr_compare.py`）与评测（`tools/gt_eval.py`）。

表格类报告（血常规/尿常规/血糖/肝肾功能/甲状腺功能）的后处理，从「用 OCR 行框启发式重建表格几何」改为「表格结构识别（TSR）模型还原网格 + 语义列映射」。选定 **RapidAI TableStructureRec**（`wired_table_rec` + `lineless_table_rec`，ONNX 推理；**同时运行两个子模型并择优**，不依赖 `table_cls` 单模型路由）。叙述体（超声 `mode=narrative`）**不适用**，保留现有行内配对。词典数据文件与报告契约的字段语义不变。

## 背景

P3 review 发现：`postprocess._extract_items`/`_role_centers` 的几何重建对版式自适应差、依赖绝对像素容差，坏例（lft_05）会把元数据标签误判为列中心而丢行；每来一批新版式就要改解析代码。词典（数据文件、真实语料门禁）本身是稳的，脆弱点在**几何层**。设计计划 §10 已预告可换 PP-Structure/SLANet。

## 原型对比（2026-10-10，24 张真实样本）

方法：复用已存 OCR 框（不重复 OCR），跑三个方案，指标 `clean` = 该类别词典命中项里「独占一个单元格」的比例（左右双栏兼容；同格合并 ≥2 项记失败）。脚本：`recognizer/tools/tsr_compare.py`。叙述体样本不适用。

| 方案 | 输入 | n | 退化(行列<2) | clean 均值 | clean 最低 |
|------|------|---|-------------|-----------|-----------|
| SLANet_plus（rapid_table） | 整页 | 21 | 4 | 0.35 | 0.00 |
| SLANet_plus（rapid_table） | 裁剪到表格 | 21 | 0 | 0.63 | 0.00 |
| TableStructureRec（`table_cls` 路由） | 整页 | 21 | 2 | 0.84 | 0.00 |
| **TableStructureRec（wired+lineless 择优）** | 整页 | 21 | **0** | **0.97** | **0.80** |

- SLANet_plus **必须裁剪表格**才不退化，即便裁剪后仍显著落后。
- `table_cls` 会把有线表误判为无线（如 cbc_01），导致少数样本走错子模型而退化（lft_05/tft_02/cbc_04）；**同时跑 wired+lineless 择优即全部恢复**（lft_05 从 7×1 恢复到 26 行 49 格）。
- 结论：TableStructureRec 胜出；且不采用 `table_cls` 单模型路由。

## Considered Options

- **PP-StructureV3（PaddleOCR）**：能力最全（含版面/表格检测），但依赖 PaddlePaddle；macOS Apple Silicon 无官方 wheel（需源码编译），与现有 onnxruntime 栈冲突，本地开发不可用。否。
- **SLANet_plus（rapid_table，ONNX）**：同栈、轻，但必须裁剪且精度落后（0.63 vs 0.97）。否。
- **Table Transformer（TATR）**：DETR 系，公开评测精度更低、依赖 transformers/torch 更重。否。
- **维持启发式，只做加固（相对容差、表头元数据排除）**：成本最低，但不解决版式自适应的天花板。作为 TSR 退化时的**回退**保留，不作为主路径。

## Consequences

- 仅 `mode=table` 走 TSR；`mode=narrative`（超声）不变。
- TSR 需要**原图**（裁格/复识别），而 `/reparse` 原仅持 OCR 结果 → 采用**契约方案 A**：OCR 结果契约增**可选** `table_structure`（`html` + `model` + `elapse`），`/report` 填充并随 `ocr_results` 落库，`/reparse` 复用它（不再读原图），NF-05 闭环保持。已同步 `schemas/ocr_result.schema.json` 与 Go `internal/contract`（NF-06）。（相对原型设计省去 `cell_boxes`/`logic_points`：postprocess 只需 HTML 网格。**此取舍已被 §5 修正**：只存 HTML 会使适配器丢失坐标、无法修复模型的并格/错位；若要让网格与 OCR 几何对齐，应改为存 `cell_bboxes`（像素框）。）
- `wired-table-rec`/`lineless-table-rec` 声明 `requires_python <3.13`；本项目原锁 3.13 → **决策：识别服务降至 Python 3.12**（官方支持区间）。
- 模型为运行时从 ModelScope 下载 → 已纳入 `deploy/recognizer.Dockerfile` 构建期预下载，运行时离线可用（NF-01）。
- golden 已重基：OCR golden 增 `table_structure`；报告 golden 仅 lft_05 变化（17 → **19 项**），其余 23 张不变。
- 单张新增耗时：TSR 子模型 ~0.7s（CPU）+ 可选检测；仍在 NF-04 <3s 量级内。
- 指标 `clean` 只衡量「名称独占格」的结构正确性，**不含**数值/单位/参考范围的正确配对；数值解析仍由词典 + `_decompose` 承担，须在集成验收中另行验证。

## 实测复核与根因（2026-10-11）：不采用

维护者提供**真实数据对照** `samples/expected/vl/*.json`（视觉模型 + LLM 结构化，禁改基准）。19 个有 GT 的样本、274 项；指标为相对 GT 的「抽到项数 / value 对 / unit 对 / ref 对」。评测脚本 `recognizer/tools/gt_eval.py`。

### 1. 口径修正：原记录高估了差距

- **有序对齐应使用 LCS 而非贪心**：原 `_align` 是贪心匹配，方案一旦漏掉 GT 开头若干项即级联崩溃（旧启发式 lft_05 只算 2/19、ua_04 只算 5/24）。改用最长公共子序列后，启发式 249→**263**、网格 148→**162**。
- **阅读顺序偏差**：双栏单据（cbc/ua 系列）GT 为**列优先**（左栏整列→右栏整列），网格输出为**行优先**；有序口径因此系统性罚网格——同一批预测，集合口径网格 **196** vs 有序 162。
- **首版「网格→项」映射有实现缺陷**（见 §3(a)）；仅修复这些缺陷即令网格 162→**209**。

### 2. 对照结果（matched 为修正后的 LCS，/274）

| 方案 | matched | value 对 | unit 对 | ref 对 |
|---|---|---|---|---|
| **现状启发式** | **263** | **239** | **191** | **184** |
| 网格·首版（仅 HTML） | 162 | 97 | 70 | 75 |
| 网格·修复版（仅 HTML） | 209 | 147 | 123 | 113 |
| 网格·几何对齐（`cell_bboxes` + OCR 框） | 253 | 184 | 126 | 91 |

原记录（贪心口径）：启发式 249/239/191/184、网格 148/112/84/86、网格+回填 148/131/100/99。启发式数字可复现；**网格数字不可复现**（同版本实测 148/97/70/75，见 §4）。另：A 变体（启发式「行区间归属」配对）劣于现状（同线版式错配，cbc_04 ref 14→1），已弃。

### 3. 为什么网格抽取准确率低于启发式

**（a）「网格→项」映射层缺陷（可修，但首版显著拉低了网格）**

- `_grid_header` 要求**同一行**同时含「名称/代号列」与「结果列」，遇到表头被并入首行（lft_01）、两行表头（tft_02）、定性尿检无「结果」列（ua_04）即返回 `None` → **整张 0 项**；
- 值/单位/参考的扫描以「下一个名称列」为界，而代号列紧邻名称列，**代号不是词典别名时值被整体跳过**（lft_05 19 项里 17 项 `value=None`）；
- **无左右半栏建模**，扫描会越界吞掉另一半栏的格（cbc_01 红细胞 unit=`EON`）；
- `parse_grid` 不展开 `rowspan/colspan`（模型几乎每个 `<td>` 都带 colspan）→ 列索引跨行错位；合并表头格（`项目名称 结果`、`单位 参考值`）直接丢列。

**（b）模型输出自身的缺陷（几何对齐也修不掉，是根本原因）**

- **并格**：名称+值并一格、单位+参考并一格、甚至**跨行值并一格**（lft_04 `280.86`=28 与 0.86、`44.836.6`、`224.08`；cbc_05 `4.00~10.000~9/L`）；
- **列错位/漏列**：代号列被放进错误半栏（cbc_01 `EON`）、右半栏名称列用指标名当表头而漏出（cbc_04/cbc_05）、表头行吞掉首条数据名并整体下移（lft_01）；
- **两行表头**（tft_02）。

这些错误只有**按列中心做逐列几何配对**才能恢复——而那正是启发式已经在做的事。

**（c）架构层面的根本原因**

- 契约只存 `table_structure.html`（原型阶段明确省去 `cell_boxes`/`logic_points`），网格适配器**拿不到坐标**，无法把模型并格/错位的 cell 映射回 OCR 几何；
- 启发式直接持有 OCR 的 x/y，对上述模型噪声天然免疫；
- 因此「以 HTML 网格为唯一信息」的适配器存在**结构性天花板**：模型越并格，网格越失真，而它又没有坐标可纠。

### 4. 事实核查（记录订正）

- **lft_05「17→19 由 TSR 修复」不成立**：该 2 项实际由同一提交里的 `_match_name` 多形态匹配（`_name_forms`，处理 `1 *丙氨酸氨基转移酶` 的序号+星号）与词典别名 `天门冬氨酸氨基转移酶` 恢复；**当前启发式单独即可 19/19**。原「几何层丢 ALT/AST」的归因不准确。
- **本 ADR 原记录的网格数字（148/112/84/86）不可复现**（同版本实测 148/97/70/75）；启发式数字可复现。
- **「wired+lineless 择优」实测等价于「只用 lineless」**：24 张样本 `wired` 从未胜出（多数直接退化，少数格数远少于 lineless）；§3.4 的择优理由不成立。
- **原型 `clean=0.97` 只测「名称独占格」**，不含 value/unit/ref 配对与阅读顺序，严重高估真实抽取质量（此判断正确）。

### 5. 几何对齐实验（2026-10-11）

按「把 `cell_bboxes` 纳入契约、让网格与 OCR 几何对齐」的思路复测：重跑 TableStructureRec 取每个 cell 的**像素框**，把 OCR 行按像素中心归入 cell；**网格给行、几何给列**。

- 结果（§2 末行）：matched **209→253**（几乎追平启发式 263），但 value/unit/ref **184/126/91** 仍低于 239/191/184；
- 残差全部指向 §3(b) 的模型并格/错位——即**几何对齐能纠正「名称列被打乱」，纠正不了「模型把多条记录的值/单位/参考并进一格」**；
- 「TSR 行分割 + 启发式列几何」是纯启发式的**严格超集**：保留启发式全部脆弱逻辑（表头关键词集、像素容差、半栏切分、y 距离配对），再叠加模型依赖、契约扩展与离线运维，且不更优——**纯启发式支配该混合方案**。

### 结论

**不采用 TSR 网格抽取，启发式为主路径。** 原因不是「TSR 模型识别得差」，而是：网格适配器丢弃了 OCR 几何，无法修复模型自身的并格/错位；要修复就必须补回逐列几何，而那正是启发式。原型（`tools/tsr_compare.py`）与评测（`tools/gt_eval.py`）保留，供后续以真实数据迭代（重点 unit/ref）。
