# 0019 · 护理记录导航与孩子上下文：B3 + appbar tabs

**状态：** 采纳（2026-11-23）；已实现并通过跨票验收（2026-11-24，含 spec §15 已知差异）。

## 背景

- 产品当前是家庭检查报告档案；长期要加入「日常护理记录」（喂养、尿布、睡眠、辅食）。用户已确认**日常记录优先**，并在 A / B1 / B2 / B3 四套原型中选择 **B3**。
- B3 的结构是：一级域「育儿 / 健康档案」；底部只显示当前域的二级视图。育儿底部是「今天 / 统计」，健康档案底部是「报告 / 趋势」。
- 一级导航的呈现方式在「顶部独立 segmented / appbar tabs / 标题下拉 / 首页双卡」中比较后，用户确认 **appbar tabs**：把「育儿 / 健康档案」放进 appbar，省掉独立一行，两个域仍始终可见。
- 爸爸、妈妈可能各自用自己的设备记录同一个孩子。当前产品是 **LAN-first、无账号**（ADR-0006），成员列表由家庭后端共享，但「当前选中哪个成员」是每台设备的本地状态。若没有显式的孩子上下文，两台设备可能在不同孩子名下记录，或误记到成人成员。
- 详细页面、状态和验收见 `.scratch/care-log/spec.md`；可点击原型见 `.scratch/care-log/prototype/prototype.html`（B3）与 `nav.html`（一级导航对比）。

## 决策

1. **B3 两级导航，最多两层。** appbar 放一级域「育儿 / 健康档案」；底部放当前域的二级视图：育儿为「今天 / 统计」，健康档案为「报告 / 趋势」。不新增第三层；「记录」是今天页上的动作，不是 tab。
2. **一级域嵌进 appbar。** appbar 左侧是「育儿 | 健康档案」文本 tab；健康档案 tab 带待核对小圆点。当前孩子不再放 appbar，而是育儿页内容区左上角「豆豆 ▾」，避免与域 tab 争位置（2026-11-23 体验定稿）。进入育儿后，底部不再出现健康档案。顶部独立 segmented 只作为 appbar 放不下时的 fallback；标题下拉与首页双卡不采用。
3. **当前孩子按设备本地保存，不做全局 active child。** 单孩子家庭自动选中该孩子；多孩子家庭在每台设备选择并记住（App 本地存储）。成员列表来自共享后端，但「当前孩子」不写入服务端全局状态——两台设备可能同时记录不同孩子。护理事件以 `member_id` 为唯一归属，不以设备状态为准。
4. **记录目标必须显式。** 今天页 hero 显示「豆豆 · 距上次喂养」；记录弹层标题下显示「记录给 豆豆 · 当前孩子」。多孩子时必须先选目标孩子才能保存；单孩子显示目标但锁定。育儿只对 `is_child` 成员开放；育儿页只消费当前孩子，不受当前成员是成人影响。
5. **重复记录提示，不自动去重。** 同一孩子、同类型（喂养）在短时间窗口内已有记录时，保存前提示「刚刚已有一条喂养记录，仍然添加？」由家长决定是否继续。建议窗口 5 分钟，具体阈值在 spec 中定义。提示是客户端行为，不改变事件数据；不做服务端去重。
6. **不做账号，也不做记录人归属。** 沿用 ADR-0006：LAN-first、无鉴权；不存 `recorded_by`、不显示爸爸/妈妈头像或名字，所有护理事件标「家长记录」。无法可靠识别操作者时，不制造假归属；如未来需要远程协作或真实记录人，另开 ADR 评审账号、权限、审计与儿童数据合规。
7. **提醒不是 tab。** 提醒是设置，不是育儿视图；保留在今天页卡片 + 提醒设置入口，默认关闭、只在本机、用户设定间隔、不承诺准时。等出现多种提醒类型、提醒计划或提醒历史，再评估独立入口。
8. **统计留在育儿的二级视图。** 统计不升为一级域；B3 统计页接入 `charts.html` 的 4 指标（喂养 / 奶量 / 睡眠 / 尿布）× 3 图表类型（柱状 / 堆叠 / 折线）。图表类型只在统计页内部切换，不增加导航层级。

## 后果

- 两台设备各自保留「当前孩子」；如果爸爸在豆豆、妈妈在老二，两边都能记录，但每条事件带明确 `member_id`。UI 必须在育儿页左上角、hero、记录弹层三处显示目标孩子，不能只靠本地选择。
- 单孩子家庭没有额外选择成本；多孩子家庭每台设备首次选择一次，之后记住。换设备或清除 App 数据后需要重新选择。
- 重复记录提示是 best-effort：两台设备都可能在窗口内各记一次；提示能减少误记，但不能消除。没有账号，不能判断「谁记的」。
- appbar tabs 省 46px，但 appbar 会更满；如果未来加入通知、搜索等动作，回退到顶部独立 segmented（B3 的 A 呈现）。回退只改呈现，不改两级结构。
- 健康档案仍是报告、核对、趋势的主路径；育儿不替代报告，也不把护理事件写进报告趋势或分析快照。
- 本 ADR 不定义 `feeding_events` 表与 API；护理事件数据模型、契约和 E2E 另立 spec。当前 spec 只锁定导航、孩子上下文、记录目标与重复提示。

## 实现状态（2026-11-24）

- 票 01–08 已实现并通过跨票验收；详细差异、已知限制与验收证据以 `.scratch/care-log/spec.md` §15 和 `.scratch/care-log/issues/08-acceptance-and-regression.md` 为准。
- 关键偏差：用户可见「日常」改名「育儿」，路由与域标识统一为 `/care`（旧 `/daily` 本地偏好自动迁移）；当前孩子在育儿页内容区左上角；护理事件仍为客户端内存 adapter（无正式表 / API / 迁移）；提醒与统计均为本机 / 7 天口径，不写报告、趋势或分析快照。

## Considered Options

- **A 档案优先**：报告档案仍是首页，护理从成员卡进入。否——用户确认日常记录优先。
- **B1 平铺三 tab**：今天 / 统计 / 档案同级。否——「档案」是域，和「今天 / 统计」不是同一层。
- **B2 底部固定日常 / 健康档案（现称育儿），顶部今天 / 统计**：域切换最快，但高频视图在顶部。否——用户确认高频视图放底部。
- **B3 + appbar tabs**：一级域在 appbar，二级视图在底部。采纳。
- **C 标题下拉**：省空间，但另个域藏在一次点击后；待核对角标也不可见。否。
- **D 首页双卡**：并列最清楚，但每天第一次记录多一次点击；对「两个人轮流记同一个孩子」不如 B 直接。否。
- **全局 active child**：服务端保存一个「当前孩子」，所有设备同步。否——两台设备可能同时记录不同孩子，全局状态会互相覆盖。
- **账号 / 记录人归属**：能显示谁记的，但需要账号、鉴权、TLS、审计和儿童数据合规；与 ADR-0006 冲突。否。

## 残余风险

- 多孩子家庭仍可能选错孩子；只能靠三处显式显示 + 记录弹层确认降低，不能保证为零。
- 重复记录提示可能误报（例如两次真实喂养间隔很短）或漏报（超过窗口）；不做自动去重是明确取舍。
- appbar tabs 在 390px 下可用，但加入更多动作后会拥挤；回退方案是顶部独立 segmented，需要重新截图与测试。
- 没有真实用户验证：爸爸/妈妈同时使用的频率、孩子切换频率、重复记录窗口都还是假设；上线前按 `.scratch/care-log/spec.md` 的验收与 smoke 清单验证。
