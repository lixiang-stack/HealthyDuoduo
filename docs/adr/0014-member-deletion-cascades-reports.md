# 0014 · 成员删除级联删除其报告

**状态：** 采纳（2026-10-30）。

## 背景

- 成员此前只支持建 / 列 / 改，不提供删除；误建的成员只能一直留着。
- `reports.member_id` 是 `REFERENCES members(id)` 且没有 `ON DELETE`；直接删有报告的成员会被外键挡住。
- 报告删除已有硬删语义（级联指标项 / 修正对，原图与 OCR 历史保留）；成员删除必须选一个报告归属策略。

## 决策

1. `DELETE /api/v1/members/{member_id}` 硬删成员及其全部报告：报告、指标项、修正对级联删除；`images` 与 `ocr_results` 保留，同一张图日后可以重新上传。
2. 存储适配器单事务：先 `DELETE reports WHERE member_id = $1`，再 `DELETE members WHERE id = $1`；外键保持 `NO ACTION`，不新增迁移。
3. App 删除前读取该成员报告数，确认面板写明「及其 N 份报告」与「此操作不可恢复」；取不到报告数不允许删除。
4. 删除当前成员时清除 `CurrentMemberContext` 与 AsyncStorage；其他成员与无主报告不受影响。
5. 成员不存在返回 404；成功 204。

## Considered Options

- **有报告就阻止删除**：安全，但清理误建成员时需要逐份改派 / 删除报告，摩擦大。否。
- **报告改为无主（`member_id=null`）**：需要新增「未归属」视图，否则报告在 App 里直接消失。否。
- **软删除成员**：保留恢复能力，但增加 `deleted_at`、过滤与恢复入口，本期收益不足。否。
- **数据库 `ON DELETE CASCADE`**：SQL 更短，但把破坏性规则永久下沉到数据库，未来任何删成员路径都会静默级联。否；由存储适配器单事务显式执行。

## 后果

- 删除成员不可恢复；原图与 OCR 历史仍在，但 App 内不再有对应报告。
- 报告删除与成员删除都是硬删；无回收站。
- 文档与测试需同步：`CONTEXT.md`、设计文档、spec、OpenAPI、RNTL 屏幕测试与存储 smoke。
- 若未来需要批量改派或软删除，按新需求评审，不回退到「禁止删除」。
