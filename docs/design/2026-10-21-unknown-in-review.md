# 2026-10-21 未知指标项是否进入核对队列

## 为什么做

票 01 的审计给出一个反直觉的事实：`unknown` 占指标项的约四分之一（`member=aaa` 43/188，samples 130/559），但其中绝大多数不是「抽取不可信」，而是「值与参考范围无法比较」这一结果语义。当前核对队列只收「未核对的低置信项」，未知项只在徽标里出现。需要决定：要不要把未知项拉进核对，以及如果拉，拉哪些、怎么计数、怎么和 `partial` 区分。

## 结论

**推荐：保持「核对」队列只收低置信项；不把全部未知塞进队列；如果产品要帮家长补数据，另开一个只在报告详情出现的「待补录」小节，不进入概览计数、不新增状态。** 同时把可消除的未知项当作识别缺陷在识别端修，而不是长期让家长兜底。

理由（按重要性）：

1. **队列语义会被打散**：`待核对` 现在只表示「这次抽取不可信，请你确认或修正」。未知项里有 87% 的样本项没有可执行动作（定性、单侧比较、区间结果、纸面没有参考范围）；把它们塞进同一个队列，家长会遇到大量「点进去什么也做不了」的卡片。
2. **未知与报告状态不同轴**：`unknown` 不参与 `status` 派生；`member=aaa` 43 个未知全部落在 `success` 报告里。把未知计入「待核对 N 份」会让概览计数与报告真实状态打架。
3. **可操作比例低且可预测**：按现有修正语义，能消除未知的只有「缺数值 + 参考范围可解析」与「参考范围上下界写反」两类，合计 `member=aaa` 11/43（25.6%）、samples 17/130（13.1%）。为这 13%–26% 增加一套全局队列/契约字段，收益与成本不匹配；先在详情页给入口更划算。
4. **真正该修的是数据链路**：这 11/17 项里有原图证据表明值/范围是印着的（抗 Jo-1 `1.53`、淋巴细胞 `22.8%`、cbc_04 的 `3.5--9.5`）。长期用核对流程兜底，会把识别 bug 变成家长的日常劳动。

## 现状（决策基线）

- **核对队列**：`pendingItems(items) = review_status === 'unreviewed' && low_confidence`（`apps/mobile/src/review/items.ts`）。
- **队列入口**：上传返回分岔（`needsReview` = `partial` 或含未核对低置信项）与详情页「逐项核对 N 项低置信」。
- **报告级徽标**：`unreviewed_low_confidence_count` 只统计 `partial` 报告的未核对低置信项（ADR-0005）；`flag_counts.unknown` 只是展示徽标，不参与待办。
- **概览待处理**：`partial` 且非影像单的份数 + 这些报告的未核对低置信项之和（`reports/overview.ts`）。
- **状态派生**：`partial` 由「任一 value 为空 / 日期缺失 / 低置信占比 ≥ 50%」触发；未知不触发。
- **动作语义**：确认只改 `review_status`；修正才重算 flag（`internal/pipeline/review.go`、ADR-0005）。

### 审计事实对决策的约束

| 事实 | 数值 | 对队列决策的含义 |
| --- | --- | --- |
| 未知占全部指标项 | aaa 22.9% / samples 23.3% | 全部进队列会显著拉长队列 |
| 未知项中低置信的 | aaa 2 / samples 4 | 未知与低置信几乎不重叠，不能相互替代 |
| 可被现有修正消除 | aaa 11/43 / samples 17/130 | 可操作项是少数，但仍值得给入口 |
| 不可被修正消除 | aaa 32/43 / samples 113/130 | 全部进队列会产生大量无动作卡片 |
| 未知项所在报告为 success | aaa 43/43 | 未知不能计入「待核对份数」 |
| 影像单未知 | 0 | 不需要为影像单设计未知队列 |

## 可操作未知的判定

“可操作”只按**现有修正能否把 flag 从 unknown 变成可比结果**定义：

| 条件 | 动作 | 修正后 |
| --- | --- | --- |
| `value == null` 且参考范围可解析（`a-b` / `a~b` / 单侧比较 / 性别前缀） | 补数值 | 可能 normal/high/low |
| 参考范围可解析但上下界写反 | 修参考范围 | 可能 normal/high/low |
| `value` 数字 + `ref_range == null` 且 `raw_text` 含范围 token | 补参考范围 | 可能 normal/high/low |
| `value` 为定性文本 / 单侧比较 / 区间结果 | 无 | 仍是 unknown（修正只能改善显示值） |
| `value` 数字 + `ref_range == null` 且 `raw_text` 无范围 token | 无 | 不能编造参考范围 |
| `ref_range` 不可解析 | 修参考范围 | 可能 normal/high/low（当前 0 例） |

审计中「数字 + 缺范围 + raw_text 有范围 token」为 0 例，第一版实现可以不做这条；等真实数据出现再加，避免无证据的机制。

## 选项对比

| 选项 | 队列内容 | `member=aaa` 队列长度 | samples 队列长度 | 优点 | 代价 / 风险 |
| --- | --- | ---: | ---: | --- | --- |
| **A. 保持现状** | 未核对低置信项 | 1（ANA(IIF)，unknown） | 17（其中 4 项也是 unknown） | 语义单一；队列短；与核对页 `pendingItems` 一致 | 可操作的未知（如抗 Jo-1 缺值）只能靠家长自己翻详情发现；概览只算 partial，success 报告的低置信项会让队列与概览不一致 |
| **B. 全部未知进队列** | 低置信项 + 全部 unknown（去重） | 43 | 143 | 不漏任何未知 | 74%–87% 无动作；「待核对」同时表示不可信与不可比；概览计数与 `success` 冲突；家长认知负担最大 |
| **C1. 可操作未知进全局独立队列** | 低置信项 + 可操作 unknown（去重） | 12 | 32 | 只暴露能改的项；动作明确 | 需要在 `ReportSummary` 新增派生计数或逐份拉详情；概览多一个「待补录 N 项」；补录完成不一定翻转 `partial`，需要解释 |
| **C2. 可操作未知只在报告详情出现** | 低置信队列不变；详情页「待补录 N 项（未知）」只列**非未核对低置信**的可操作未知（高置信，或低置信但已确认） | 11 | 15 | 不改契约/概览/状态；入口贴近原图与修正动作；不与核对队列重复 | 发现路径依赖用户打开详情；不是全局待办 |

> `member=aaa` 当前有 6 个 `low_confidence` 项，其中 5 个已被确认（`review_status=confirmed`），实际 `pendingItems` 只剩 1 个（ANA(IIF)，且它本身也是 unknown）。这也说明「低置信」与「未核对」不是同一集合：队列长度按 `pendingItems` 算，不是按 `low_confidence` 算。
>
> C2 只收高置信可操作未知：低置信且未核对的项已经在核对队列/核对页里，重复列到「待补录」会让同一项出现两个入口。低置信但已确认、仍缺数据的项可以进入 C2（它们已不在核对队列）。
>
> **队列与概览的已知差异**：`pendingItems` 看 `low_confidence && unreviewed`，不看报告状态；`unreviewed_low_confidence_count` / 概览「待核对」只统计 `partial` 报告。因此 `member=aaa` 的 ANA(IIF) 会出现在核对页（队列 1），但概览显示 0。这不是本次引入的问题，但 C1 若把补录计数放进概览，必须显式决定是否沿用 `partial` 过滤，否则会出现同类不一致。


**不推荐 B。** B 的问题是结构性的：它把「抽取可信度」和「比较结果」压进同一个「待核对」标签，而这个标签已经承载了 `partial`、`unreviewed_low_confidence_count` 和概览计数三套口径，再加一层就无法解释。

**推荐 A + C2。** A 保证现有核对语义不变；C2 给可操作未知一个近场入口，但不新增状态、不改概览、不伪造全局待办。若后续真实数据显示家长确实需要从首页看到补录任务，再评估 C1 的契约成本。

## C2 的队列模型（若采纳）

### 列表与计数

- **位置**：报告详情页，指标项列表上方（`ReportCard` 之后），非影像单且报告非 `failed` 时渲染。
- **标题**：`待补录 N 项（未知）`；N=0 不渲染。
- **列表**：本报告内满足「可操作未知」且**不属于未核对低置信项**的指标项（低置信未核对项已在核对队列，避免同一项两个入口）。可操作判定见上节。
- **分区，不重复**：C2 项从下方的普通指标项列表中移出；C2 存在时，普通列表标题改为 `指标项（M）`，M = 总项数 − N。每项只渲染一次；N=0 时保持现有 `指标项（总数）` 标题。
- **排序**：两个分区各自保持报告原始项序（与核对页一致），不另排序。
- **不进入**：核对页 `pendingItems`、`needsReview`、上传分岔、时间线/概览徽标、`status` 派生、`unreviewed_low_confidence_count`。
- **动作**：只提供「修正/补录」入口（打开四项事实编辑器，缺失字段为空）；**不显示「确认」**——确认不会改变未知。
- **完成后**：修正响应返回该项；若 flag 变为 normal/high/low，或 value 已非空，该项从「待补录」列表移出。若修正后仍是 unknown（例如补了定性值），也移出——列表衡量的是「数据是否补齐」，不是「unknown 是否消失」。
- **无「忽略/稍后」状态**：第一版不引入第三套状态。纸面确实没有值的项会一直留在列表里；这是诚实的缺口提示，后续用使用反馈决定是否加「无法补录」标记。

### 与现有状态的关系

| 概念 | 是否受影响 |
| --- | --- |
| `status=partial` | 不变；补录不会自动翻转（服务端只按未核对低置信计数翻转） |
| `unreviewed_low_confidence_count` | 不变 |
| `pendingItems` / 核对页 | 不变 |
| 概览「待核对 N 份 / M 项」 | 不变 |
| `flag_counts.unknown` | 修正后按响应重算（现有 `applyReviewResult` 已做） |
| 确认/修正语义 | 不变；C2 只是修正的一个入口 |

> 注意：补录完成但 `partial` 仍为 `partial` 是预期行为——缺日期、缺值等 partial 触发条件不在核对状态机里。C2 文案不要承诺「补完就变成功」，只说「补齐后按值×范围重算」。

### 概览与文案

- 概览**不新增**「待补录」计数；现有「待核对」口径保持 `partial`。
- 详情页空态/提示文案：`照原图补齐数值或参考范围；未知项不会因确认而改变。`
- 报告详情「逐项核对 N 项低置信」入口保持原样；C2 与其下方的普通指标项列表是**分区**关系：C2 项不再出现在普通列表，避免同一项两个入口。

### 需要更新的文档

- `CONTEXT.md`「核对」定义补一句：核对队列只收未核对低置信项；`unknown` 是结果状态，不是待办。**（2026-10-21 已更新）**
- `docs/design/2026-10-13-viz-and-client-spec.md` 5.2 的核对范围备注：unknown 不参与 `partial`、不进核对队列；C2 是详情页的补录入口。**（2026-10-21 已加修订注）**
- `docs/design/2026-10-21-unknown-flag-audit.md`（票 01）作为数据依据，不重复粘贴。
- 不需要新 ADR：C2 是客户端派生视图，不改契约/存储/状态机；若未来做 C1（全局计数），再评估是否需要 ADR。

## 验收标准（C2 实现票）

另立 `.scratch/review-clarity/issues/05-pending-backfill-section.md`（`Status: ready-for-human`，等维护者确认是否本期做）。实现票至少覆盖：

- 纯逻辑 `backfillItems(items)`：只返回可操作未知，保持原序；排除未核对低置信项（已在核对队列）；测试矩阵覆盖缺值+可解析范围、上下界写反、定性值、单侧比较、区间值、数字+缺范围、无 `ocr_lines`、低置信未核对。
- 详情页小节 `待补录 N 项（未知）`：N=0 不渲染；影像单/failed 不渲染；每项复用 `ReviewItemCard` 的编辑器与「查看原图定位」，不显示确认。
- 修正后可操作项移出列表；`applyReviewResult` 重算徽标；核对页与概览计数不变。
- 单测覆盖纯逻辑与组件可见性；App E2E 用 `cbc_04`（含可操作未知：缺值与上下界写反）覆盖入口与修正后移出；`cbc_01` 的中性细胞数作为「不可操作」反例（不出现在列表）。
- 不新增依赖、不改 OpenAPI、不改数据库。
