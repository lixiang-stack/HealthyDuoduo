# GLM-OCR vs RapidOCR：医学检查单识别基准

**状态：** 调研结论（2026-11-25）。未采纳生产替换。
**代码基线：** `origin/main` `edcc05b`（2026-11-25 同步后 rebase）。
**范围：** `samples/` 内 19 份有原图、有逐项真值的检查单；剔除 1 份真值不符后，18 份 / 267 个指标项参与打分。另 3 份超声只计时、不参与字段打分。
**数据与脚本：** `.scratch/ocr-bench/`。原始输出不提交（`raw/` 已 ignore）。
**原始问题：** 在医学检查单识别领域，GLM-OCR 是否比 RapidOCR 效果更佳？能否同时满足“准确率高、资源利用率低”？

## 结论

1. **准确率：GLM-OCR 在字段恢复上确实更好，但优势集中在难样本。**
   - 值 + 单位 + 参考范围全部正确：RapidOCR 195/267（73.0%）→ GLM-OCR 237/267（88.8%），**+15.7pp**。
   - 配对 McNemar：GLM 独对 54 项、RapidOCR 独对 12 项，**p = 1.7e-7**；18 份样本中 GLM 胜 13、平 2、负 3。
   - 分字段：值 88.0%→94.8%，单位 82.1%→90.8%，参考范围 84.5%→94.0%。

2. **资源：GLM-OCR 全面更重，不符合“资源利用率低”的相对口径。**
   - 热延迟中位数 **1.22s → 5.74s（4.7×）**，p95 **1.77s → 11.45s（6.5×）**。
   - 模型 **30.3MB → 2.7GB（约 89×）**；峰值内存 **约 0.6GB CPU → 2.7GB 且 100% GPU**。
   - 冷启动约 **3.9s → 14s**；吞吐约 **49 → 10 张/分钟**（单实例、本机实测）。

3. **工程：GLM-OCR 不能直接替换 RapidOCR。**
   - GLM 默认输出文本 / Markdown / HTML（结构化 JSON prompt 也不稳定），**没有 boxes、scores、行号**；现有 `OCRResult` 契约、几何列对齐后处理、`raw_text` / `ocr_line_numbers` 核对链路都无法复用。
   - 输出格式不稳定：同一批样本中出现 HTML 表格、Markdown 表格、纯文本三种形态；存在 `colspan` 合并、单位与参考范围粘连、列塌缩。
   - 因此“GLM 的 88.8%”是**行段字段恢复率**，不是最终结构化报告正确率；要进生产必须重写无坐标后处理。

**建议：** 维持 RapidOCR 主链路；先修它暴露出的规则缺口（定性结果、单位/上标归一、倾斜/双栏）。若准确率优先级高于资源，做 **GLM 兜底/难样本路由**，而不是全量替换；全量替换前需接受 2.7GB GPU 占用、5–15s/张，并完成无坐标解析器与 100+ 张真人核对验收。

## 为什么做

当前 recognizer 使用本地 RapidOCR（PP-OCRv6 small + 规则后处理）。实测在倾斜表格、双栏、尿常规定性结果、上标单位等场景会漏值或错列。GLM-OCR 是 0.9B 文档 OCR 模型，`glm-ocr:latest` 经 Ollama 本地部署，模型仅 2.7GB，看起来适合替代。问题是要用数据回答：

- 在真实脱敏检查单上，GLM 的字段准确率是否真的更高？
- 它的资源代价是否满足“资源利用率低”？
- 现有后处理/契约能否直接迁移？

## 调研过程与讨论

### 1. 初始假设与反例

初始假设是“GLM-OCR 是 0.9B 文档模型，模型只有 2.7GB，应该比 PP-OCRv6 small 更准”。为避免直接为这个假设找证据，先列能推翻它的反例：

1. **可能只是 RapidOCR 后处理坏了，不是 OCR 识别差。** 若如此，修规则比换引擎便宜。
2. **GLM 文本更准，但表格结构更差。** 若如此，不能直接替换，反而需要新解析器。
3. **GLM 只在难样本上赢，清洁样本反而更差。** 若如此，应做路由而不是全量替换。
4. **指标对 GLM 更宽松。** 若如此，换同一套指标跑 RapidOCR 原始 box，结论应消失。
5. **差异来自真值错误。** 若如此，剔除可疑样本后结论应消失。

实测结果：第 1、2、3 条都成立，第 4、5 条不成立。

- 第 1 条：`ua_01` 的定性值在 RapidOCR 原始文本里大多已读到，是后处理置 `null`；`cbc_04` 的列错位也主要来自几何聚类/规则。
- 第 2 条：`cbc_02` 的单位列塌缩、`ua_04` 的 `colspan` 合并、`lft_02/lft_04` 的名称误读，说明 GLM 的结构输出不能直接当表用。
- 第 3 条：RapidOCR ≥90% 的 5 份清洁样本上，RapidOCR 100%、GLM 92.5%；GLM 的总体优势来自 13 份难样本。
- 第 4 条：同一套行段指标跑 RapidOCR 原始 box 是 74.2%，生产后处理是 73.0%，与 GLM 88.8% 的差距稳定存在。
- 第 5 条：剔除 `cbc_03` 后差距反而略增；剩余真值 typo 对两引擎都有影响，但不足以解释 15pp。

### 2. 指标选择：为什么不用 CER / 全文字符准确率

最初的直觉是算 CER（字符错误率），但本仓库没有可用的人工逐字真值：

- `samples/expected/ocr/<id>.json` 是 **RapidOCR 自己生成的回归 golden**（见 `samples/README.md`）。拿它当 CER 真值，RapidOCR 会被构造性地打成 0 错误，不能比较。
- `samples/expected/vl/<id>.json` 只有逐项字段，没有页眉/页脚/叙述文的逐字真值；全页 CER 还会把双栏的阅读顺序差异算成字符错误（例如同一行左右两栏的先后），与“识别准不准”不是一回事。
- 纯文本 OCR 的正确性最终要落到“项目名—值—单位—参考范围”的对应关系；只比字符 bag-of-words 会放过串列、漏项、单位错配。

因此最终采用**字段级恢复率**：

- RapidOCR：直接跑现有 `run_postprocess`，优先用报告 item 的 `raw_value/raw_unit/raw_ref_range`，缺失时回退 `value/unit/ref_range`。
- GLM：无生产解析器，按输出行/表格单元格定位项目名，取到下一个项目名之前的文本段，检查值/单位/参考范围是否原样出现。
- 另用同一套行段指标跑 RapidOCR 原始 box 做交叉验证（74.2% vs 88.8%），排除“只对 GLM 宽松”的偏差。

### 3. 评估过的其他口径（均未作为主指标）

| 口径 | 做法 | 为什么不用 |
|---|---|---|
| 全页 CER | 对 `expected/ocr` 或人工转写算编辑距离 | `expected/ocr` 是 RapidOCR 自己的输出；无人工全页真值；双栏阅读顺序会造成假错误 |
| 全局字段覆盖 | 值/单位/参考范围是否在全文任意位置出现 | 不校验归属；`%`、`g/L` 等常见单位会被其他行“蹭对”；去空白后参考范围会和下一行行号粘连 |
| 数值 multiset recall | 统计全文数字 token 的多重集召回 | 同样不校验归属；日期、编号、参考范围会污染结果；对“值串到别的项目”不敏感 |
| GLM 结构化 JSON | 用 JSON schema prompt 让 GLM 直接输出 items | 试点 3 份均不可直接使用：`lft_02` 只返回项目名列表，`ua_01` 双栏串列（`尿潜血` 的 `3+` 被当成 abbr、`阴性` 被当成 value） |
| 生产报告对生产报告 | 两引擎都产出 Report 再比 | GLM 没有生产解析器；强行写一个解析器会把“解析器质量”混进“OCR 质量” |

最终主指标是“行段字段恢复率”，并用生产 RapidOCR 报告做基线；两者定义接近，但文中明确标注 GLM 的数字**不是**最终结构化报告正确率。

### 4. 结构化 JSON 试验（为什么不能直接让 GLM 出结构化结果）

试点 prompt：

```text
请按下列JSON格式输出图中所有检验项目，按印刷顺序，不要输出解释：
{"items":[{"name":"","abbr":"","value":"","unit":"","ref_range":""}]}
```

结果：

- `cbc_01`：能返回 25 条 JSON，但 `name` 填的是缩写（`WBC`），中文名放在 `abbr`；字段语义已经漂移。
- `lft_02`：`items` 退化成字符串数组，只保留项目名，值和单位全部丢失。
- `ua_01`：双栏表格串列——`尿潜血` 的 `name=尿潜血, abbr=3+, value=阴性, unit=%, ref_range=31%`，把右栏的 `异性红细胞率% 31%` 拼进来了。

结论：GLM-OCR 的强项是**版面文本识别**，不是稳定的结构化抽取；直接用它替代“OCR + 规则后处理”会在结构化层引入新的、不可控的错误。官方 `glmocr` SDK 集成 PP-DocLayoutV3，理论上可能补回布局/结构化能力，但本次 Ollama 路径未验证，且会引入新的依赖与资源开销，不能当作已解决的方案。

### 5. 方案取舍（奥卡姆剃刀）

在“准确率 + 低资源”的双目标下，机制最少的方案不是换引擎，而是：

1. 先修 RapidOCR 已暴露的规则缺口（定性值、上标/单位、倾斜/双栏、名称别名），用同一 267 项验收。
2. 只有规则修完后仍不达标的难样本，才引入 GLM 兜底；且必须配独立解析器与 box 回退。
3. 全量 GLM 是机制最多、资源最重的方案，只在“准确率压倒资源”且 GPU 预算明确时考虑。

## 做什么（基准设计）

### 数据

- **18 份检查单 / 267 项**：血常规 cbc 4 份、生化 lft 5 份、血糖 glu 3 份、激素 tft 3 份、尿常规 ua 3 份。全部来自 `samples/` 的真实脱敏图像。
- **真值**：`samples/expected/vl/<id>.json`（视觉模型 + LLM 逐项结构化，仓库约定“禁改”）。只使用 `name/abbr/value/unit/ref_range`。
- **剔除 `cbc_03`**：其 VL 真值是 24 项完整血常规，但图像实际是 16 行外周血细胞形态报告（约 12 项）；两引擎都只能命中 6–7 个名字，属于真值与图像不符，不是引擎差异。未修改 VL 文件。
- **7 项 GT 结果为空的指标**（均在 `ua_05`）不参与“结果正确”打分，避免把真值缺失算成引擎错误。
- **3 份超声**（`us_01..03`）没有逐项真值，只进入延迟统计；叙述文准确性未量化。

### 两个引擎的“最佳可用路径”

| | RapidOCR | GLM-OCR |
|---|---|---|
| 模型 | PP-OCRv6 small det/rec + PP-OCRv4 mobile cls | `glm-ocr:latest`（F16，0.9B + 视觉编码器） |
| 运行 | onnxruntime，CPU | Ollama / llama.cpp，Metal GPU |
| 输入 | 原图 | 原图，prompt `Table Recognition:`，`num_ctx=16384`，`temperature=0` |
| 结构化 | 现有 `run_postprocess` 产出 Report items | 无生产解析器；按行/单元格切段评估 |

RapidOCR 用**现有生产后处理**的输出打分（item 的 `raw_value/raw_unit/raw_ref_range` 对 VL 真值）；GLM 因无坐标，采用**行段恢复**：在输出行/表格单元格中定位项目名，取到下一个项目名之前的文本段，检查值/单位/参考范围是否原样出现。两者都做 NFKC、全半角、`μ/u`、`×10^9`/`*10^9`/`10^9`、波浪号/长短横线归一。

为避免“GLM 的指标更宽松”这一质疑，另用**同一套行段指标**直接跑 RapidOCR 原始 box（不经过生产后处理）：74.2% vs GLM 88.8%（同一 267 项口径），与生产口径的 73.0% vs 88.8% 基本一致，说明差距不是后处理口径造成的。

### 资源测量

- 机器：MacBook Pro M1 Pro / 32GB / macOS 14.6.1。
- RapidOCR：同进程先 warm-up，再逐张计时；`/usr/bin/time -l` 测峰值 RSS。
- GLM：Ollama 已加载模型后逐张请求；`wall_s` 含 HTTP、图像预处理、prefill、decode；`ollama ps` 记录模型占用与处理器。
- 延迟均为热态；冷启动单独记录。未测功耗/能耗（需要 sudo `powermetrics`）。

### 2. 优势集中在难样本

按 RapidOCR 的样本准确率切分：

| 分层 | 样本 | 项数 | RapidOCR | GLM-OCR |
|---|---|---:|---:|---:|
| RapidOCR ≥90%（清洁版式） | cbc_01/02、glu_03、lft_02/04 | 80 | **80（100%）** | 74（92.5%） |
| RapidOCR <90%（难版式） | 其余 13 份 | 187 | **115（61.5%）** | **163（87.2%）** |

结论：**清洁版式上 RapidOCR 已经接近满分，GLM 反而低 7.5pp；GLM 的总体优势来自倾斜/双栏/定性结果等难样本。** 这直接支持“路由/兜底”，不支持“全量替换”。

### 3. 典型胜负

**GLM 赢的样本**

- `cbc_04`（96% vs 54%）：图像主表轻微倾斜、左侧还有竖排扫描条；RapidOCR 的 box 行聚类把列打乱，参考范围读成 `130--31`、`8210--1` 等；GLM 仍按视觉行读出 `4.53 / 4.3--5.8 / 10^12/L`。
- `ua_01`（96% vs 59%）：尿常规定性值 `3+ / +- / norm.`；RapidOCR 原始文本多数能读到，但后处理把定性值置为 `null`（`ocr_miss`），报告层丢失；GLM 的表格行保留了值。
- `lft_05`（100% vs 79%）：多栏 + 单位/参考范围列；RapidOCR 出现单位与参考范围粘连/串列，GLM 行内列序完整。
- `tft_03`（57% vs 14%）：低质量小字；两引擎都不到 60%，但 GLM 少错几项。

**GLM 输的样本**

- `cbc_02`（88% vs 100%）：GLM 的“单位”列塌缩——红细胞分布宽度两行把 `↑` 放进单位格、血小板单位丢失；RapidOCR 后处理反而稳定。
- `lft_04`（85% vs 100%）：GLM 把 `丙氨酸氨基转移酶` 读成 `内氨酸氨基转移酶`，名称未命中；RapidOCR 全对。
- `lft_02`（94% vs 100%）：GLM 把 `r-谷氨酰转移酶` 读成 `α-谷氨酰转移酶`，名称未命中；属于字符误读，不是数字识别问题。

**GLM 的失败模式（采用前必须处理）**

- 无坐标：不能生成 `OCRResult.boxes/scores`，现有 `run_postprocess`、核对页 `ocr_line_numbers`、低置信标记全部失效。
- 输出形态不稳定：HTML 表格 / Markdown / 纯文本混用；`colspan` 把定性结果的“结果/参考范围”合并，直接按列解析会错位。
- 单位与参考范围粘连：`7-40U/L`、`4.3--5.8 10^12/L`；需要单位词典回切。
- 偶发数字误读：`tft_01` 的 FT4 读成 `0.33`（真值 `10.33`），且单位 `mmol/L` 与 `nmol/L` 混；这类错误在 0.5B 解码器上仍会出现。
- 列塌缩：`cbc_02` 的 RDW 单位、PLT 单位丢失；`ua_04` 的 `colspan` 行。

**RapidOCR 的失败模式**

- 行碎片化：姓名/项目名/单位被切成多个 box；`姓` + `☑名：`。
- 上标丢失：`10^9/L` → `109/L`、`10^12/L` → `1012/L`。
- 单位与参考范围被检测成一行：`*10~9/L 3.5-9.5`。
- 倾斜/双栏时列归属漂移；尿常规定性值在后处理层丢失。
- 这些多数是**规则/几何问题**，不是字符识别本身；先用规则修复可能以更低成本拿回一部分 GLM 的收益。

补充：

- GLM 的 `wall_s` 包含 HTTP 与 Ollama 调度；本机 `ollama ps` 显示 `glm-ocr:latest` 为 `2.7 GB / 100% GPU / context 16384`。
- 如果“资源利用率低”指**绝对占用**（无 GPU、低内存、低延迟），GLM 明确不满足；如果指**模型规模可接受、能本地跑**（0.9B / 2.7GB），GLM 可以接受，但仍比 RapidOCR 重一个数量级。
- 未测 q8_0 量化、CPU-only 推理、批量并发；这些会改变绝对数字，但不改变“GLM 更重”的方向。

## 怎么实施（如果继续）

### 方案 A：保留 RapidOCR，先修规则（推荐先做）

优先修基准中暴露的、无需换引擎的缺口：

1. 定性结果：`3+ / +- / norm. / 阴性` 进入 `value`，不要一律 `null`；这是 `ua_01` 差距的主因。
2. 单位/上标归一：`10^9`、`10*9`、`109` 的识别与回切；单位与参考范围粘连时按词典最长匹配切开。
3. 倾斜/双栏：用表头带拟合斜率或列中心校准，修 `cbc_04` 类样本。
4. 名称别名：`r-/γ-/α-谷氨酰转移酶`、`间接/同接胆红素` 等加入词典/归一。

验收：在同样 267 项上，字段完整率从 73.0% 提升到 ≥85%，且不引入新的 partial/failed 回归。

### 方案 B：GLM 兜底/难样本路由（准确率优先，资源可控）

- RapidOCR 先跑；满足以下任一条件才调 GLM：`status != success`、可操作 unknown 比例高、OCR 平均置信度低、检测到明显倾斜/多栏、图像质量低。
- GLM 结果进入**独立的无坐标解析器**：按 header 角色解析 HTML/Markdown 表格，纯文本走行段 + 词典；不要复用 `run_postprocess`。
- 保留 RapidOCR 的 box 结果作为核对/展示的几何来源，GLM 只提供更正后的文本/字段；否则核对页无法定位原文。
- 成本：只对难样本付费。以本基准 13/18 难样本估算，平均延迟约 `1.2 + 0.72×5.7 ≈ 5.3s`；若生产 80% 是清洁样本，则约 `1.2 + 0.2×5.7 ≈ 2.3s`。**需要生产分布数据才能定论。**

### 方案 C：全量 GLM（仅在准确率压倒资源时）

- 需接受：2.7GB GPU 常驻、5–15s/张、无 box 契约、输出形态不稳定。
- 需要新建：GLM 表格/行解析器、字段归一、无坐标的核对定位、失败回退。
- 验收门槛建议：100+ 张真人核对样本；结构化报告三项全对 ≥90%；p95 延迟 ≤5s（或业务可接受值）；显存 ≤4GB；失败样本可回退 RapidOCR。

## 数据质量与局限

- `cbc_03` 的 VL 真值与图像不符（24 项 vs 约 12 项），已剔除；这是既有数据问题，未改 `samples/expected/vl`。
- VL 真值由视觉模型 + LLM 生成，**不是人工逐字核对**；`lft_04` 的 `同接胆红素`、`天冬氨酸氨基转移`，`cbc_05` 的 `0.9/L`（应为 `10^9/L`）等真值噪声会同时压低两引擎，且对 GLM 的原始名称匹配更不利。建议正式决策前人工抽查 3–5 份。
- 样本仅 18 份，且以本仓库已有的脱敏样本为主；未覆盖 90°/180° 旋转、强反光、折痕、低照度、多页等真实场景。
- GLM 只测了 `Table Recognition:` + F16；`Text Recognition:` 在试点中文本几乎一致，未单独跑全量；q8_0、CPU-only、并发未测。
- 延迟是单机 M1 Pro 的热态数字；服务端 CPU/GPU、容器、并发下的绝对值会不同，但“GLM 更重”的方向预计不变。
- 指标是**字段恢复代理**，不是端到端报告正确率；GLM 没有生产解析器，无法给出同口径的最终报告准确率。

## 决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | 主指标用“字段完整率”，不用全页 CER | 无人工全页真值；`expected/ocr` 是 RapidOCR 自身输出；双栏阅读顺序会造成假 CER |
| D2 | 剔除 `cbc_03`；`ua_05` 的 7 项空结果不参与“结果正确”分母 | 前者 VL 真值与图像不符；后者是真值缺失，不是引擎错误 |
| D3 | RapidOCR 用生产后处理作为基线；GLM 用行段恢复 | GLM 无生产解析器；用同口径行段指标跑 RapidOCR 原始 box 做交叉验证，差距稳定 |
| D4 | 不做全量替换 | 准确率 +15.7pp 成立，但资源 4.7× 延迟 / 89× 模型 / GPU 占用，且无 box 契约 |
| D5 | 下一步先修 RapidOCR 规则，再做难样本路由评估 | 相当一部分 GLM 优势来自定性值、单位/上标、倾斜双栏、名称别名等规则缺口；机制最少 |
| D6 | 本阶段不改生产代码/契约 | 调研任务；GLM 接入需要新的无坐标解析器与核对 UI 方案，另立 spec |

## 开放问题

1. **生产分布**：真实上传中“清洁版式”占比多少？若 ≥80%，路由方案的期望延迟约 2.3s；若难样本占多数，路由省不了多少，反而增加两套链路的维护成本。
2. **真值质量**：VL 真值是模型生成，需要人工逐字核对 3–5 份（优先 `cbc_02`、`cbc_04`、`ua_01`、`lft_04`、`tft_01`），再决定是否把本次差距写进验收门槛。
3. **布局能力**：官方 `glmocr` SDK + PP-DocLayoutV3 是否能提供稳定 layout/表格结构？若能，是否能映射回现有 `OCRResult.boxes`/核对定位？未验证。
4. **资源边界**：q8_0、CPU-only、容器内并发、显存上限 4GB 时的实际延迟/质量；本次只测 F16 + Metal。
5. **无坐标核对**：如果 GLM 不返回 box，核对页如何定位原文？是否接受“只展示整页 + 字段高亮”而非行号定位？这是产品交互决策，不是 OCR 决策。
6. **覆盖场景**：90°/180° 旋转、强反光、折痕、低照度、多页、叙述型超声/病历；本次只有 18 份实验室检查单 + 3 份超声计时。
