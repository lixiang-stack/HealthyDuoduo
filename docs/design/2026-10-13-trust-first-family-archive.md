# 信任纵切的家庭健康档案（Trust-First Family Archive）

**来源：** 对可视化与客户端需求文档（同目录 `2026-10-13-viz-and-client-spec.md`）的发散与收敛，2026-10-13。
**关系：** 本页记录发散收敛的决策依据；`2026-10-13-viz-and-client-spec.md`（v1.3）已同步采纳本页结论——里程碑重切（M0–M5）、条件核对、双入口核对闭环、离线队列、二维码配对、「较上次」Δ、趋势信任标记与单位门控、成员卡片首页——并收录下方「拷问记录」的收敛结论。页面规格细节以其为准（下文简称「需求文档」）。

## Problem Statement

家长如何能在 30 秒内把一张纸质检查单变成**可信、可比、长期不丢**的家庭健康档案——而家长不懂检验医学、OCR 又识别得不完美？

## Recommended Direction

**D1 信任纵切：产品的灵魂是「屏幕上的每个数要么高置信、要么经家长亲手确信」。** 第一个可用纵切面就是「拍照 → 核对 → 确信这个数」，档案（时间线/详情/趋势）是核对过的数据的视图。核对是**条件触发**的（2026-10-13 补充决策）：仅 `status` 为 `partial`/`failed` 或含低置信项的报告进入核对流程，干净的成功报告（`success` 且全量 `low_confidence=false`）**免核对**、零摩擦直落档案。需核对的报告走**同一个闭环的两个入口**：在家拍照，结果秒回（识别服务同步、NF-04 <3s），纸还在手上时当场核对（V1）；在医院拍照，离线队列回家自动同步，同步完成的瞬间提醒核对，纸通常当天还在（V2 兜底：低置信项在阅读时顺手确认）。报告状态从「全部处理完才回收」的作业模式，改为「剩余 N 项未核对」的**派生**状态——没有作业就没有作业被放弃的问题。

**客户端与后端 HTTP API 同仓一起做，代价与机会都集中在 M0 契约冻结。** 三个现状硬事实要在 M0 一次清偿：仓库目前没有任何面向客户端的 HTTP API（`cmd/hdd` 是 CLI）；`report.schema.json` 无 member 概念（B1 是契约变更 + 存储迁移 + golden 重基）；指标项没有任何指向 OCR 行的链接（核对「缩放到对应区域」在契约上不成立）。B3 落库按「**修正对可回流**」形状设计（原值→修正值 + `raw_text` + 行号，可查询）——本期只存不回流，但形状必须一次到位，未来直接喂 `gt_eval`。

**局域网先行的必然后果是产品性的，不是技术细节。** 离线队列与「后端不可达」是 App 的一等状态而非错误；上传页的进度条升级为「排队中，回家自动传」；`hdd` 或局域网页面显示**配对二维码**，App 扫一次完成 Base URL 配置（从需求文档原 P1 升 P0）。

**成功标准：** 家里至少一位非开发者日常真实使用它拍照、归档并核对。

## Key Assumptions to Validate

- [ ] **家长真的会核对**（灵魂假设）— M1 后观察自家第一次真实上传的核对行为；错了则降级为需求文档已有的「查看图像提醒」。
- [ ] **大部分核对机会发生在纸还在手上时** — 回顾自家过去半年检查单的实际拍照场景（在家拍 vs 医院拍完当天回家）；错了则核对延迟数天，体验打折但不死。
- [ ] **同名指标跨院可经单位门控/换算得到可信趋势** — 拿自家两个医院的真实同名指标实测 `unit_families` 覆盖度；错了则趋势分段不连线，只展示。
- [ ] **同步识别 <3s 在手机 Wi-Fi 上的等待体验可接受** — 机器侧 NF-04 已证，人侧在 M1 验证环境实测。
- [ ] **成员最小模型（名字 + 排序 + 是否孩子）撑得起一期** — 上传归属与首页卡片够用即可。

## Not Doing (and Why)

- **鉴权与公网部署** — 局域网先行是本期决策；家庭健康数据出本机需另行立项评审。
- **医生分享/导出** — 「复诊时刻」未当选灵魂；Δ（V5）已给 80% 比较价值，成本一个数量级更低。
- **年龄分段参考范围叠加** — 违反决策 #8（范围一律从检查单抽取）；那是数据真相之外的加工。
- **修正数据回流 `gt_eval` 的实现** — 只按可回流形状存（D3 纪律），回流本身下期立项。
- **第二用户/长辈共享** — 自家自用单设备假设，核心闭环验证后再谈。
- **筛选/排序** — 需求文档 P1 保留在 M5，不提前。
- **对干净报告（`success` 且全量高置信）的核对流程** — 状态与置信度已保证可信，核对是纯摩擦；核对仅对 `partial`/`failed`/低置信报告触发。
- **砍掉趋势（V6）** — 已被明确排除；趋势保留本期（M4）。

## 拷问记录（2026-10-13，设计树收敛）

对本页与需求文档的三轮拷问（grill-with-docs）已把设计树走到无未决分支。关键收敛（规格细节以需求文档 v1.3 为准，数据模型与安全姿态另见 ADR-0005 / ADR-0006）：

- **域规则**：空 `items` ⇒ `failed`（识别端保证的不变量）；`failed` 不进「待核对」计数，出口 = 重拍新报告、老报告留痕沉底。核对状态机 = 决策可重复（每次修正 append 修正对）、无撤销、报告状态派生单调（partial→success 单向，success/failed 恒定）；确认不产生记录。修正字段集 = value / unit / name / ref_range 四个纸面事实，`flag` 服务端按 value×ref_range 重算、不接受手改；详情页**任意项**可修正（免核对 ≠ 不可修改）；`report_items` 永远装最终生效值、修正对 append-only（ADR-0005）。成员最小模型 = 显示名 + 是否孩子；一份报告恰好归属一个成员；改归属/删除报告进 P0（并入 M1）。
- **契约**：HTTP 契约载体 = OpenAPI 3.1（`schemas/openapi.yaml`，`$ref` 复用识别端 schema）；API 面 12 端点定稿（`/api/v1` 前缀、item 用 BIGSERIAL `item_id` 不透明句柄、sha256 命中幂等返回 `duplicate:true`、新增 `fail_reason` 列、`--force` 对已核对报告 409）；`ocr_lines` 内嵌详情响应。M0 收缩 = 新增 migrations（member / 核对状态 / 修正对 / `fail_reason`）+ OpenAPI + HTTP fixtures，**识别端契约与存量 golden 不动**。
- **趋势与 B2**：连接键 = 规范名 + 归一单位；Δ 基线 = 同键内 `report_date` 严格更早的最近一份（无日期/仅同日不显示）；跨单位族点段本期不连线、不提示——印形归一（`unit_families`）在 ingest 已完成，无运行时换算、无系数表，留给未来真实需求驱动。新增风险登记：跨院 alias 覆盖率 M4 前实测（真实双院数据），低则补词典 alias，不做模糊匹配。
- **部署与配对**：`hdd serve` 单二进制子命令（复用 `deps` 编排层；compose 已有 postgres/seaweedfs/recognizer，仅缺 hdd 服务）；**Mac（arm64）= 开发验证实例（M1）**、**NAS（amd64）= 家庭常驻实例（M2）**，同一份 compose 两处复用、镜像双架构；DHCP 保留 IP → 配对二维码 = 纯 URL 常量（ADR-0006）。Expo Go 只验「前台重试」语义，dev client 与后台静默续传为 M2 加分项非门禁。
- **环境事实勘误（拷问中核实）**：`report_items.value` 已为 TEXT（`migrations/0002_item_value_to_text.sql`），`method` 列已存在（`0003_item_method.sql`）——需求文档对 value 字符串原样的依赖无存储障碍。
