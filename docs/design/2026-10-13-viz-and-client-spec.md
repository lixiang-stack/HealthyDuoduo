# 需求文档：可视化与客户端

**产品：** HealthyDuoduo（健康多多）  
**范围：** 仅可视化与客户端（不含 OCR、结构化、存储实现）  
**版本：** 1.3  
**日期：** 2026-10-13  
**变更：** 1.0 → 1.1：确定多成员（家庭定位）、趋势可视化纳入本期范围、低置信复核确认落库；修正状态枚举与统一语言。1.1 → 1.2：核对改为条件触发（仅 `partial`/`failed`/低置信报告需核对，干净 `success` 免核对）；核对双入口化（上传当场 + 详情顺手）并提前进 M1；新增 M0 契约冻结；离线队列与二维码配对升 P0；新增「较上次」Δ、趋势信任标记与单位门控、成员卡片首页。1.2 → 1.3：拷问收敛（设计树全分支闭合，记录见 trust-first 文档「拷问记录」）——M0 收缩（识别端契约与存量 golden 不动）；HTTP API 面 v0 定稿（OpenAPI 3.1 载体）；核对状态机定稿（决策可重复·无撤销·派生单调）；修正字段集改为 value/unit/name/ref_range 且 `flag` 服务端重算；详情页任意项可修正；空 `items` ⇒ `failed` 不变量且 `failed` 不进待核对计数；Δ 基线细则；趋势单位门控收紧（跨单位族不连线不提示、无运行时换算）；改归属/删除进 P0 并入 M1；9.3 用例扩为六条；部署双实例（Mac arm64 验证 / NAS amd64 常驻）。决策依据：`docs/design/2026-10-13-trust-first-family-archive.md`。

## 1. 目标

1. **产品主形态为 App**（iOS / Android）：完成检查单上传、档案列表、详情（结构化结果、状态、图像）。  
2. **产品定位家庭成员健康检测**：支持家庭各成员（孩子为重点）各自的报告归档、趋势与状态分析。  
3. **Web 仅用于本地验证**：在浏览器中快速验收页面逻辑与 API 联调，不作为正式对外产品入口。  
4. 客户端 **不实现** OCR、规则抽取、模型推理；只调用后端 HTTP API。  
5. **单一前端工程**：业务界面一份源码；验证环境与 App 共用同一套页面逻辑。  
6. **数字可信为灵魂，核对为条件触发**：屏幕上的数字要么来自高置信识别、要么经家长核对。仅 `status` 为 `partial` / `failed` 或存在 `low_confidence: true` 指标项的报告进入核对流程；`success` 且全部指标项 `low_confidence=false` 的报告**免核对**，零摩擦直落档案。

## 2. 原则

| 原则           | 说明                                              |
| -------------- | ------------------------------------------------- |
| App 优先       | 功能是否交付，以 App 可运行的主路径为准           |
| 家庭多成员     | 以成员为档案主轴；孩子是重点，但不是唯一           |
| Web 只做验证   | Web 用于开发自测与演示流程；可不对外部署          |
| 先验证后上 App | 每次 UI/交互改动：先在验证环境通过，再在 App 确认 |
| 单工程         | 禁止为 App 再维护第二套业务页面                   |
| API 驱动       | 字段、状态、图像地址以后端为准                    |
| 平台能力隔离   | 选图：验证环境用文件选择；App 用相机/相册         |
| 文案中性       | 不出现诊断、处方类表述                            |

## 3. 端定位与研发节奏

### 3.1 定位

| 端      | 定位                                                                |
| ------- | ------------------------------------------------------------------- |
| **App** | 产品主目标；家长实际使用；必须支持相机/相册上传                     |
| **Web** | 本地验证环境；用文件选择跑通与 App 相同的业务路径（上传→列表→详情） |

### 3.2 固定节奏

```text
改动提出
  → 在验证环境实现并验收（Web / Expo 浏览器或模拟器，见选型）
  → 验证通过
  → 在 App 目标上确认（含相机等原生能力）
  → 本迭代完成
```

**要求：**

- 验证未通过，不得标记为 App 已完成。  
- 形成 App 后 **保留验证通道**，后续迭代仍先验证再同步 App。  
- 不删除验证用 Web/预览目标；可不公网部署。

## 4. 技术选型（锁定）

### 4.1 主路径

| 项       | 选择                                                               |
| -------- | ------------------------------------------------------------------ |
| 框架     | **React + Expo（React Native）**                                   |
| 产品     | Expo 构建 **iOS / Android**                                        |
| 本地验证 | **Expo Go / 模拟器** 为主；必要时 **Expo Web** 辅助大屏看列表/详情 |
| 语言     | TypeScript                                                         |

**锁定理由（与目标对齐）：**

- 产品根在 App，与「App 优先」一致。  
- Expo Go / 模拟器可快速看效果，满足「先验证再真机」的节奏。  
- 相机、相册、权限等原生能力路径成熟。

### 4.2 验证环境约定

| 验证手段                     | 用途                             |
| ---------------------------- | -------------------------------- |
| Expo Go / iOS·Android 模拟器 | 日常改 UI、联调 API 的首选验证   |
| Expo Web                     | 可选；方便桌面大屏查看表格类详情 |
| 真机安装包                   | App 侧正式验收（尤其相机、权限） |

上传在验证环境可用 **相册/文件类 API 或开发期选图**；**产品验收必须覆盖相机或系统相册**。

### 4.3 不采用的主路径

- 以 Web 壳（Capacitor）为产品根的方案作为默认锁定（与 App 优先目标不如 Expo 贴合）。  
- 原生双端分项目维护业务 UI。  
- 微信小程序作为本期产品主形态。

## 5. 功能需求

### 5.1 信息架构

```text
App / 验证环境
├── 成员（家庭档案入口：成员列表 / 切换；孩子排前）
│   └── 某成员的
│       ├── 报告时间线（按当前成员过滤；成员卡片首页上线前兼作首页）
│       ├── 报告详情
│       ├── 指标趋势（同名指标跨报告）
│       └── 上传（默认归属当前成员）
└── 设置（API Base URL：二维码配对优先，手输兜底）
```

上传入口既在成员上下文内，也保留全局上传后选成员的路径（后端未支持成员时按 P1 缓）。

（P1）成员入口升级为**成员卡片首页**：每张卡片给出中性事实摘要——最近一次报告类别与距今、偏高/偏低计数、待核对数、报告总数；第一屏回答「现在有什么值得留意」。文案严格停在事实侧（如「距上次 4 个月」），不做建议（如「该复查了」）。四个数字的口径（1.3 拷问定稿）：偏高/偏低计数 = **最近一次报告内**按 flag 计数；「距上次」= 最近**任意类别**报告；待核对数 = **跨报告累计**未核对低置信项；报告总数 = 该成员全部报告。

### 5.2 页面

#### 报告时间线（P0；成员卡片首页上线前兼作首页）

- 展示：类型、时间、状态、成员（有则显示）。  
- 状态区分：`success` / `partial` / `failed`（文案：识别完成 / 待核对 / 识别失败；与 report.schema 一致；含 `low_confidence` 指标项、核对未完成的报告归入「待核对」氛围，核对完成后状态由 B3 更新）。  
- `failed` 报告**不计入**「待核对」计数（无可核对项，1.3 定稿）；出口是重新拍照生成新报告，原报告留痕沉底。  
- 异常计数徽标：每张卡片显示如「3 项偏高」等按 `flag` 聚合的摘要（P0 仅计数与「待核对」数）。
- 点击进入详情；空列表引导上传；加载与错误可重试。  
- （P1）按类型、日期筛选或排序。

#### 成员（P0）

- 成员列表与切换；孩子优先展示。  
- 最小模型（1.3 定稿）：**显示名 + 是否孩子**两档信息，仅此；无生日/头像，不提供成员删除（可改名）。排序 = 孩子优先、其余按创建序（客户端排序）。  
- 一份报告恰好归属一个成员；多成员同单（如家庭套餐混单）是已知限制（P2+）。  
- 选中成员决定时间线、上传归属、趋势范围（默认当前成员）。  

#### 报告详情（P0）

- 结构化指标项：名称、数值、单位、参考范围、`flag` 染色（normal 绿 / high、high→红、low→蓝/黄、unknown→灰，具体色板实施期定）。  
- **指标条带（本页视觉核心）**：解析 `ref_range` 渲染参考范围条，按位置打点当前值；`'<2.00'`（点置于条端外）、`'70-80'`（区间无点）等形态分别有约定，规格见 5.3。  
- `low_confidence: true` 的指标项高亮，并提供「我要核对」入口（见核对闭环）。**任意指标项均可发起修正**（走同一 B3 路径，1.3 定稿）——「免核对」指无强制流程，不等于不可修改：高置信 ≠ 正确，家长发现明显错值必须有出口（重传同图会被 sha256 去重挡回，且重跑结果相同）。  
- （P1）「较上次」Δ：指标项旁显示如「较上次 ↑2.1（3 个月前）」。基线细则（1.3 定稿）：上一值 = 同成员 + 同规范名 + 同归一单位、`report_date` **严格早于**当前报告日期的最近一份（与上传先后无关）；任一方无日期或仅有同日报告 → 不显示 Δ（宁缺毋错）。纯事实陈述，不做解读。  
- 报告级：类型、状态、失败原因/分数（后端提供则显示）。  
- 可查看图像。  
- 识别失败时仍尽量展示图像与原因（原因来自 M0 契约新增的 `fail_reason`，由 pipeline 产出，1.3 定稿）。  
- （P2）数据来源标识（规则 / 模型 / 混合）。

#### 核对闭环（P0；上传当场 + 详情顺手，双入口同一闭环）

**触发条件（条件核对，不过度打扰）：**

- 仅当报告 `status` 为 `partial` / `failed`，或任一指标项 `low_confidence: true` 时进入核对。  
- `success` 且全部指标项 `low_confidence=false` 的报告**免核对**：上传后直接归档，无强制核对流程——但详情页任意指标项仍可发起修正（免核对 ≠ 不可修改）。  
- `items` 为空的报告一律 `failed`（识别端保证的不变量，1.3 定稿）；`failed` 无可核对项，不计入「待核对」计数。  

**双入口：**

- **上传当场（首选时机）**：上传返回结果即呈现核对界面——纸通常还在手边，逐项滑过「确认 / 修正」。针对 `low_confidence` 指标项：图像（缩放到对应区域，定位依赖 B3 的 item→OCR 行号链接）↔ `raw_text` ↔ 解析值/参考范围 三方对照。  
- **详情顺手（兜底时机）**：详情页点开高亮的低置信项即对照核对；报告以「剩余 N 项未核对」呈现，无显式「全部处理完」提交步骤。  
- `failed` 报告无可核对指标项：核对表现为展示图像与失败原因；必要时重新拍照上传（生成新报告，原报告保留留痕）。

**操作与落库（1.3 拷问定稿）：**

- 家长操作：**确认**（认可当前解析结果，不产生记录）或 **修正**（改 value / unit / name / ref_range 四个纸面事实）；`flag` 一律由服务端按修正后的 value × ref_range 重算，**不接受手改**——flag 是纯函数，手改会造成时间线徽标（按 flag 聚合）与详情条带染色打架；纸上印 ↑ 而范围解析失败的场景，家长照纸补 ref_range 即可，flag 自然算出（与决策 #8「范围一律从检查单抽取」同源）。  
- **决策可重复**：已确认的项可再修正、已修正的可再修正/再确认；每次修正 append 一条**修正对**（before = 上次生效值 → after，含 `raw_text` 与 OCR 行号，append-only）；无「撤销回未核对」——误确认的出口是修正。  
- **落库真源**：`report_items` 永远装最终生效值，下游（时间线/趋势/B2）无脑读它；修正历史在修正对表（本期只存不回流，形状按可回流设计，未来直接喂 `gt_eval`；详见 ADR-0005）。  
- 报告状态由后端按剩余未核对低置信项**派生**（`unreviewed_low_confidence_count` 为响应派生值，不落列）：partial → success 单向、永不回退；`success` / `failed` 恒定。无「全部处理完」的显式回收动作。  
- 客户端不做比置信度更复杂的判断；核对结果以 API 为准反映到页面。

> **2026-10-21 修订（review-clarity v2）：** `unknown` 是「值与参考范围无法比较」的结果状态，不参与 `partial`、不进核对队列；核对队列仍只收未核对的低置信项。确认只在未核对的低置信且不可补录项暴露；可操作未知（缺值 + 可解析范围、参考范围上下界写反）只给补录/修正，避免确认后同一项又变成另一个待办（服务端仍保留重复确认能力，ADR-0005 状态机不变）。待补录入口已在重做审计后决定暂缓（2026-10-23，票 03）。依据：`.scratch/review-clarity-v2/spec.md`。

#### 指标趋势（P1，本期签订范围）

- 同一指标以（词典规范名 + 归一单位）为连接键，在当前成员下的跨报告折线图。  
- X 轴为 `report_date`；日期为 null 的报告不参与画线，但在图下以「缺日期 N 份」提示。  
- 每次报告一个点，悬浮/点按显示数值 + 参考范围，并含 `method`（检测方法）以解释跨院参考范围差异；参考范围以淡色带铺在图上（范围随时间变化则带分段）。  
- **信任标记**：已核对 / 高置信点为实心，未核对的低置信点为空心——不隐藏数据，也不冒充可信（`hdd trend` CLI 的默认隐藏策略对家长过强，标记为中道）。  
- **单位门控（1.3 定稿，收紧）**：连接键 = 同名（词典规范名）+ 同归一单位。单位印形归一（`unit_families`）在 ingest 时已完成，**不存在运行时换算、不建换算系数表**——跨单位族的点段本期**不连线、不提示**；更细的跨单位呈现留给未来真实需求驱动。    
- 数据来源：指标级聚合接口（见 6. 依赖 B2），客户端不自行跨报告拼装（避免把聚合逻辑双重实现）。

#### 上传（P0）

- 选择图像并上传；展示进度或 loading；上传前选/确认归属成员。  
- **离线队列**：后端不可达（如医院）是一等状态而非错误——照片入本地上传队列，回到局域网（App 前台）自动重试；同步完成时若报告需核对，提醒「N 项待核对」并给出核对入口。服务端按图像 sha256 **幂等**：命中已有报告返回 `200 + duplicate:true` + 已有报告（重试安全，1.3 定稿）；队列项删除只删队列项本身，不碰已归档报告。  
- **上传返回即分岔**：需核对的报告（触发条件见核对闭环）→ 立即进入当场核对；免核对报告 → 直接归档，轻提示完成。  
- 失败展示后端错误信息；队列项展示排队 / 失败状态并可重试。  
- **App：** 支持相机拍照、系统相册。  
- **验证环境：** 可用文件/相册类选择，用于验证上传 API 与后续页面。

#### 全局

- API Base URL 可配置（**P0**：`hdd` / 局域网页面显示配对二维码，App 扫一次即配；手输为兜底）。  
- 统一空态、错误态（P1）。  
- 客户端不做识别或后处理。

### 5.3 可视化规格约定

- **数值形态**：`value` 为字符串，可能是标量（`'18.40'`）、区间（`'70-80'`）、带不等号（`'<2.00'`）或 null/文本。条带组件需对每种形态有明确定义（点/区间/边界置外/不画点仅展示文本），实施前以 POC 定稿。  
- **单位与范围解析**：`ref_range` 同为字符串（`'115-150'`、`'<3.5'` 等）；解析逻辑客户端实现一份、集中放置，不做多套。  
- **颜色语义**：仅表示 `flag` 的「与参考范围比较」结果，不暗示诊断；`unknown` 一律中性灰。  
- **文案中性**：不做解读、评分、建议文案。

### 5.4 不做

- 客户端内 OCR/结构化。  
- 医疗诊断或用药建议。  
- 对 `success` 且全量高置信报告的核对流程（零核对摩擦，见核对闭环触发条件）。  
- 将 Web 作为正式对外生产入口（除非另行立项）。  
- 多套业务页面分端维护。

## 6. 与后端的关系

客户端依赖的逻辑能力。注意：**后端目前为 CLI（`hdd`），面向客户端的 HTTP API 整体为绿地**；本期客户端与后端同仓一起做，**契约先于实现冻结（M0）**。1.3 定稿的服务与契约形态：

- **服务形态**：`hdd serve` 子命令（单二进制，复用 `internal/pipeline` 的 `deps` 编排层）；`deploy/docker-compose.yml` 已含 postgres / seaweedfs / recognizer，仅新增 `hdd` 服务容器。  
- **契约载体**：**OpenAPI 3.1 单文件**（`schemas/openapi.yaml`），`$ref` 复用现有识别端 schema；识别端 `schemas/*.schema.json` 与 pydantic/Go 互证**不动**；App 侧 codegen 生成 TS 类型（单工程共享）。

**HTTP API 面 v0（M0 冻结范围）：**

| 方法与路径 | 用途 | 约定 |
| --- | --- | --- |
| `GET /api/v1/health` | 扫码后连通性校验 | `{ok, version}` |
| `GET /api/v1/members` | 成员列表 | 返回 `is_child`、`created_at`；排序客户端做 |
| `POST /api/v1/members` | 建成员 | `{name, is_child}` |
| `PATCH /api/v1/members/{id}` | 改名/改是否孩子 | 不提供成员删除 |
| `POST /api/v1/reports` | 上传（multipart：`image` + `member_id`） | 同步返回完整报告（NF-04 <3s）；sha256 命中 → `200 + duplicate:true` + 已有报告 |
| `GET /api/v1/reports?member_id=` | 时间线 | 状态、`unreviewed_low_confidence_count`、按 flag 异常计数 |
| `GET /api/v1/reports/{id}` | 详情 | items 含 `item_id`、核对状态、`ocr_lines: [{line, box}]`、`prev`（B2-lite Δ 上一值） |
| `GET /api/v1/images/{sha256}` | 图像 | 后端代理 SeaweedFS，局域网直出 |
| `PATCH /api/v1/reports/{id}/items/{item_id}` | 核对：确认/修正 | 修正只收 value/unit/name/ref_range；flag 服务端重算；响应含报告级状态 |
| `PATCH /api/v1/reports/{id}` | 改归属 | `{member_id}` |
| `DELETE /api/v1/reports/{id}` | 删除 | 硬删 reports/items/修正对；images/ocr_results 留痕 |
| `GET /api/v1/members/{id}/indicators/{name}/trend` | B2 趋势 | `?unit=` 门控；M4 消费、M0 冻结 |

其他契约约定：item 以 BIGSERIAL `item_id` 作不透明句柄（`--force` 重跑未核对报告会换 id，客户端刷新详情即取新；已核对报告被 `409` 挡住）；`failed` 报告新增 `fail_reason` 列（pipeline 产出）。

| 能力             | 用途             |
| ---------------- | ---------------- |
| 上传图像（必带 member_id） | 创建处理，归属成员 |
| 成员列表 / 档案（**B1，本期必需**） | 成员页与按成员过滤 |
| 报告列表（可按 member 过滤） | 时间线页           |
| 报告详情         | 字段、状态、图像 |
| **B2：指标级聚合**（先 B2-lite：同成员 + 同名同归一单位的上一值（`report_date` 严格更早），服务「较上次」Δ；后完整：跨报告按日期的时序点列，含单位一致性标记与已核对标记） | 「较上次」Δ 与指标趋势页 |
| **B3：核对确认落库**（确认 / 修正 value·unit·name·ref_range，flag 服务端重算；状态按剩余未核对低置信项派生；`ocr_lines` 内嵌；修正对按「可回流」形状落库） | 核对闭环 |

接口路径与字段以 `schemas/openapi.yaml` 为准。图像通过后端代理地址展示。

## 7. 非功能需求

- 验证环境可连接本地或局域网后端；真机联调禁止误用不可达的 `localhost`。  
- 部署形态：本期**局域网先行、不做鉴权**（家庭内网信任，健康数据不出内网，见 ADR-0006）；公网化另行立项评审。双实例（1.3 定稿）：**Mac（arm64）= 开发与验证实例（M1 验收）**，**NAS（amd64）= 家庭常驻实例（M2 验收）**；同一份 compose 两处复用，镜像双架构构建；路由器 DHCP 保留 NAS IP，配对二维码内容 = 纯 URL 常量（`http://<NAS IP>:<端口>`），手输兜底同串。  
- 上传超时与失败可感知。  
- App 申请相机/相册权限时说明用途为上传检查单。  
- 不向第三方日志输出完整健康明细（若日后埋点需单独评审）。  
- 至少在 Android 或 iOS 一端可完成产品主路径；目标为双端。

## 9. 里程碑与验收

### 9.1 门禁

每个涉及 UI 的迭代：

1. **验证门禁：** 在 Expo Go / 模拟器（或约定的 Expo Web）跑通约定用例。  
2. **App 门禁：** 真机或目标安装包跑通约定用例（含相机/相册）。  

### 9.2 里程碑

| 里程碑 | 内容                               | 验证环境           | App                  |
| ------ | ---------------------------------- | ------------------ | -------------------- |
| M0     | 契约冻结（1.3 收缩）：member（B1）· 核对落库（B3：确认/修正 + `ocr_lines` 内嵌 + 修正对可回流）· B2-lite→B2 · 上传/列表/详情/图像 HTTP API——全部进 `schemas/openapi.yaml`；新增 migrations（member / 核对状态 / 修正对 / `fail_reason`）；**识别端契约与存量 golden 不动**，golden 仅新增 HTTP fixtures | OpenAPI 与 Go/TS 生成物同步 | — |
| M1     | 信任纵切：成员（最小列表/切换）+ 拍照（平台隔离）→ 离线队列 → 上传 → 条件核对（当场 + 顺手）→ 时间线 → 详情（条带 + flag + `raw_text`）+ 自愈（改归属 / 删除报告） | 选图上传→核对→时间线→详情 | — |
| M2     | 产品主路径 + 配对                  | 回归 M1            | 相机或相册→核对→时间线→详情；二维码配对；同步完成提醒 |
| M3     | 家庭的脸：成员卡片首页 + 「较上次」Δ（B2-lite） | 先验证             | 再 App 回归          |
| M4     | 指标趋势（B2 完整聚合 + 信任标记 + 单位门控/换算 + `method` 提示） | 先验证 | 再 App 回归 |
| M5     | 筛选/空态等体验；iOS + Android 双端回归 | 回归               | 双端主路径           |

### 9.3 最小用例

**验证环境（M1 门禁，1.3 扩为六条）：**

1. 扫码配对 → 上传含低置信项样例图 → 当场核对（确认、修正各操作一次）→ 列表/详情一致；  
2. 干净 `success` 样例图 → 免核对直落档案；  
3. 任意项修正 → 时间线徽标与详情同步；  
4. 传错成员 → 改归属 → 时间线移位；  
5. 删除报告 → 时间线消失且同图可重新上传入档；  
6. `failed` 样例 → 图像 + `fail_reason` 展示，不计入「待核对」。  

**App：** 相机或相册选图上传 → 同步完成提醒（如触发）→ 核对 → 列表与详情与后端数据一致。

## 10. 成功标准

1. 家长主路径在 **App** 闭环（含相机或相册）。  
2. 日常改动可在 **验证环境** 先确认，再上 App。  
3. 仅一份业务界面源码；验证通道长期保留。  
4. 展示与后端 schema 一致。  
5. 界面不引导将结果理解为医疗诊断。  
6. 数字可信分岔成立：需核对报告经家长确认/修正后归档；干净 `success` 报告零核对摩擦直落档案。

## 11. 风险

| 风险                     | 应对                             |
| ------------------------ | -------------------------------- |
| 验证环境与 App 页面分叉  | 单工程 + 迭代门禁                |
| 只改 App 忽略验证步骤    | 未过验证门禁不算完成             |
| 选图逻辑写死在页面里     | 统一 `platform/pickImage`        |
| 把 Expo Web 当完整产品站 | 明确 Web 仅验证，产品以 App 为准 |
| 锁定 Expo 后无法进微信小游戏化/小程序生态 | 记录为已知限制；小程序如立项需另定方案（如独立小程序工程或重评估） |
| 趋势接口 B2 未按时提供   | M4 可顺延，不阻塞 M1–M3          |
| 跨院同名指标 alias 覆盖不足（连接键断裂，趋势丢点，1.3 新增） | M4 前拿自家两院真实同名指标实测词典覆盖；低则补词典 alias，不做模糊匹配 |
| 核对落库 B3 未按时提供   | 核对闭环降级为「查看图像提醒」，不阻塞主路径 |
| M0 契约冻结范围大（member/B2/B3 + 全套 HTTP API + golden 重基） | 契约一次冻结、按里程碑分期实现 |
| 家长不上手核对（灵魂假设） | 观察首个真实使用周期；不成立则降级为「查看图像提醒」 |

## 12. 边界

**本文包含：** 端定位、节奏、选型、页面（含成员、核对闭环、趋势）、可视化规格、验收、工程约束；**对后端的能力依赖（B1/B2/B3）**。  
**本文不包含：** OCR、后处理、数据库、对象存储、育儿业务扩展的实现本身。

---

**摘要：**  
产品定位**家庭成员健康检测**（孩子为重点），以 **App** 为准，技术锁定 **React + Expo**；部署**局域网先行、不做鉴权**（ADR-0006），后端 HTTP API 与客户端**同仓一起做、契约先行（M0，OpenAPI 3.1 冻结于 `schemas/openapi.yaml`，识别端契约不动）**。日常在 **Expo Go/模拟器（可选 Expo Web）** 验证，通过后在 App 确认相机等原生能力。全程 **一套界面源码**，先验证后同步 App。产品灵魂是**数字可信**：核对**条件触发**（仅 `partial`/`failed`/低置信报告；干净 `success` 免核对直落档案，但任意项可修正），**双入口**（上传当场·纸还在手边 + 详情顺手兜底），状态按**剩余未核对项派生**（决策可重复·无撤销·单调），修正落库按 **items 装最终生效值 + append-only 修正对 + flag 服务端重算**（ADR-0005）。可视化核心：**指标条带（值在参考范围的位置）**、**核对闭环（图像↔原文↔解析值对照）**、**同名指标跨报告趋势（信任标记 + 单位门控：规范名 + 归一单位，无运行时换算）**、**「较上次」Δ**。后端新增依赖：**B1 成员档案、B2 指标级聚合（B2-lite→完整）、B3 核对落库**。1.3 拷问收敛全过程见 `docs/design/2026-10-13-trust-first-family-archive.md`「拷问记录」。
